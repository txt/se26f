# N11: Debugging as Science (Oct 28)

Last week you inherited a repo and built a fence around it
(characterization tests, mutation-audited suites —
[maintenance lecture](n10.md)). This week something inside the fence
goes red, and you have to find out why — in code you did not write.

The thesis of tonight: **debugging is not an art, and it is not
staring.** Every step of it — reproducing, shrinking, locating,
fixing — has been turned into an algorithm, and the algorithms are
embarrassingly simple: binary search, counting, and mutation, pointed
at a failure instead of at a sorted array. By the end of tonight you
will have hand-executed three of these algorithms on paper, and you
will know exactly what to type at your inherited repo when it breaks
on Thursday.

The arc: debugging folklore and why it is expensive; the scientific
method applied to failures; **reproduce** (seeds, Heisenbugs);
**shrink** (delta debugging, git bisect); **locate**
(spectrum-based fault localization — Tarantula, Ochiai); **predict**
(where the next bug is, from history); **repair** (GenProg, and what
LLM repair changes); and the trap at the end of all of it
(patch overfitting — the oracle problem's revenge). Then proj3
marching orders.

## 1. The cost of not knowing where the bug is

### 1.1 Numbers worth keeping

- Classic industry folklore, confirmed every time someone measures:
  developers spend **a third to a half of their time debugging**.
  Add last week's "maintenance is most of the lifecycle" and
  debugging-other-people's-code may be the single largest activity
  in professional software engineering. It gets, typically, zero
  dedicated lectures. This is that lecture.

> "By June 1949 people had begun to realize that it was not so easy to get programs right as had at one time appeared. I well remember when this realization first came on me with full force. [...] The EDSAC was on the top floor of the building and the tape-punching and editing equipment one floor below. It was on one of my journeys between the EDSAC room and the punching equipment that "hesitating at the angles of stairs" the realization came over me with full force that a good part of the remainder of my life was going to be spent in finding errors in my own programs."
> 
-- Maurice Wilkes, Memoirs of a Computer Pioneer, MIT Press, 1985, p. 145. (The quoted phrase is from T. S. Eliot, Murder in the Cathedral.)
  
- From [week one](w1.md), the one-line stories: the PhD student's
  train/test label swap, the NASA downlink pipeline's Access
  database, the shuttle GPS. In each case the *fix* took minutes.
  The **find** took weeks and careers. Debugging cost is almost
  entirely *location* cost — which is why most of tonight is
  location algorithms.
- The etymology, since this course likes stories: the 1947 Harvard
  Mark II log contains an actual moth taped to the page — "first
  actual case of bug being found." The word is older (Edison
  complained of "bugs" in his inventions), but the moth makes the
  point that the term was born in *hardware*, where engineers
  already had systematic fault-finding disciplines. Software spent
  fifty years pretending it did not need them.

![](https://images.computerhistory.org/tdih/09september-1.jpg?w=600)

### 1.2 Why debugging alien code is different

Your proj2 instincts — "I remember writing something near there" —
are gone. On inherited code you have no memory to query, which means
the informal method (stare, recall, guess) has nothing to work with.
That is not a handicap; it is a forcing function. The systematic
methods tonight do not use memory. They use **evidence**: test
outcomes, execution traces, version history. On alien code the
scientific debugger has the same power as the author. Sometimes
more — the author "knows" things that stopped being true two
semesters ago.

### 1.3 Vocabulary, precisely (exam fodder)

From [the testing weeks](w2.md): a **fault** (defect, the bad line)
causes an **error** (bad internal state) which may become a
**failure** (observable wrong behavior). The chain matters tonight
because every technique attacks a different link:

- *Reproduce* and *shrink* work on the **failure** (the thing you
  can see).
- *Localization* works backwards from failure to **fault** (the
  thing you must edit).
- An error that never surfaces is a passed test hiding a fault —
  which is why coverage lies ([patterns recap](w6.md)) and why
  **coincidental correctness** will haunt §5.

And three species of bug, named by the community with its usual
humor:

- **Bohrbug** — deterministic, shows up every run, like the Bohr
  atom: solid, dependable. The nice kind.
- **Heisenbug** — changes behavior when you observe it. Add a
  print statement and it hides, because the print changed timing or
  memory layout. Classic causes: race conditions, uninitialized
  memory, compiler optimization differences between debug and
  release builds.
- **Mandelbug** — causes so complex and entangled (load, timing,
  state accumulated over days) that occurrence looks chaotic.
  The unemployment-system crashes of [maintenance week](n10.md)
  under 1,600% load spikes: mandelbug weather.

## 2. Debugging is hypothesis testing

### 2.1 The loop

Zeller's framing (his *Why Programs Fail* built the field's
textbook): debugging done well is the scientific method with a
debugger attached.

1. **Observe** a failure. Write down what you saw — exactly.
   "It crashes sometimes" is not an observation; "SIGSEGV at
   parser.c:1247 on input X, 3 runs out of 3" is.
2. **Hypothesize** a cause consistent with every observation so
   far. One cause. Written down.
3. **Predict** something unobserved: "if the hypothesis is true,
   then logging `n` at line 40 will show a negative value."
4. **Experiment** — run it. One variable at a time.
5. **Conclude**: hypothesis survives or dies. Either way you
   learned something *permanent*. Refine or re-hypothesize; loop.

Why insist on writing it down? Because debugging is a search, and an
unrecorded search revisits states. Everyone has debugged in a circle
at 2 a.m., retrying the same guess with minor costume changes. The
lab-notebook discipline — observations, hypotheses, kill-list —
turns a random walk into a trajectory. (It also hands your teammates
the trace when you give up at 3 a.m.; the issue tracker is the
natural notebook, and [week two's](w2.md) issue-stamping makes the
record promptable later.)

### 2.2 The anti-patterns, named

- **Shotgun debugging** — change several things, rerun, hope. When
  the failure disappears you do not know which change mattered or
  whether you merely *hid* it (a Heisenbug driven underground is
  not fixed). Violates "one variable at a time."
- **Superstition accretion** — "we always restart the service twice
  before the demo." Workarounds adopted without a cause ever being
  found. Every inherited repo has these; your proj3 triage should
  list them, because each is an undiagnosed fault with a ritual on
  top. (Recall [requirements week](w3.md): the workarounds ARE the
  requirements — here, the workarounds are the *bug reports*.)
- **The quick-fix reflex** — patch the symptom where it surfaced
  ("if result is negative, clamp to zero") instead of where the
  fault lives. The failure disappears; the error keeps flowing; the
  fault bites again downstream, now harder to localize because
  your clamp destroyed the evidence.
- **Blame the platform** — "compiler bug," "cosmic ray," "works on
  my machine." Real compiler bugs exist (McKeeman found hundreds —
  §4.4), but the prior is overwhelmingly against you. "Works on my
  machine" is an *observation*, and a useful one: it says the
  failure condition includes something that differs between the
  machines. That is a hypothesis generator, not an acquittal.

### 2.3 Rubber ducks are peer review

The famous trick — explain the bug, line by line, to a rubber duck,
and discover the answer mid-sentence — is not magic. Explaining
forces you to serialize your assumptions, and the bug is usually
living inside an assumption you had not noticed you were making.
It is the cheapest instance of this course's deepest rule: **claims
need instruments**, and an assumption spoken aloud becomes a claim
you can check. The 2026 version: the LLM is a rubber duck that talks
back. Paste the failing trace and your current hypothesis, and ask
it to argue *against* you — "what observations would this
hypothesis not explain?" The duck's value was never its answers; it
was the forced serialization. The talking duck adds adversarial
review, which from [week one](w1.md) you know to treat as plausible,
not true.

## 3. Step one, always: reproduce

### 3.1 No reproduction, no debugging

An unreproducible failure cannot be shrunk, localized, or verified
fixed — every downstream algorithm tonight *starts* with "a test
that fails." So the first move on any bug report is building a
**minimal reproducing recipe**: input + environment + steps →
failure, every time.

You already own the main tools:

- **Random Seeds** ([week two](w2.md)): "random" failures usually are not —
  they are unseeded. Reset the seed before every run; ship the seed
  in every bug report. A failure with a seed is a Bohrbug; the same
  failure without one impersonates a Heisenbug.
- **The flakiness catalogue** ([deeper testing](w5.md)): timing,
  network, test-order dependence, unseeded randomness. A bug that
  reproduces only in the full suite but not alone has
  *test-order dependence* — state leaking between tests — and that
  is a real fault (usually shared mutable state: remember the
  singleton's bill from [patterns week](w6.md)).
- **Record enough to replay.** Production systems log requests
  precisely so failures can be re-run. Your proj3 repo should too:
  when the demo crashes, the question "what exactly did you click?"
  must have an answer in a log, not a memory.

### 3.2 Heisenbugs: when observation is intervention

If adding a print makes the bug vanish, the print changed something
the bug depends on — timing, memory layout, optimization level.
Responses, in escalating order: use logging that was *already
there* (one reason production code logs constantly —
[week seven's](w7.md) log-don't-print, now justified twice); compare
debug vs release builds as an *experiment* (the difference is
evidence about the cause); suspect uninitialized memory and races
first, since they are the usual suspects; and reach for record-replay
tooling (deterministic replay debuggers) when the stakes justify it.

The deeper point echoes Bainbridge from [week one](w1.md): the
observer is part of the system. Plan your instrumentation like an
experimenter, not a tourist.

## 4. Shrink: delta debugging

### 4.1 The idea

You have a reproducing failure — an 847-character SQL query, a
20-file configuration, a 900-line HTML page — and most of it is
irrelevant. Shrinking matters because *localization effort scales
with input size*, and because a minimal example is socially
unanswerable: nobody can dismiss a one-line crash as "unrealistic."

**Delta debugging** (Zeller & Hildebrandt, *Simplifying and
isolating failure-inducing input*, TSE 2002) automates the
shrinking you would do by hand, with binary-search discipline. The
algorithm, `ddmin`, in words:

1. Split the failing input into **n chunks** (start n=2).
2. Test each chunk alone, and each **complement** (input minus one
   chunk).
3. If any smaller input still fails → adopt it, reset granularity,
   loop.
4. If nothing smaller fails → double n (finer chunks); loop.
5. Stop when n equals the input length and nothing can be removed:
   the result is **1-minimal** — removing *any single piece* makes
   the failure vanish.

Note what 1-minimal does *not* mean: not the globally smallest
failing input (that is exponential to find), just locally
irreducible — every remaining piece earns its place. In practice
that is minimal enough to read at a glance.

### 4.2 The oracle inside the loop

Each probe is answered **PASS / FAIL / UNRESOLVED**

- PASS = runs, target crash absent.
- FAIL = crash signature matches original (exception type + message, or stack location).
- UNRESOLVED = anything else. Not just a wrong crash: also syntax/parse error, timeout, env failure, process killed, crash at different stack frame. Any outcome where input never got far enough to answer "does this trigger the bug?"
  - Key distinction: UNRESOLVED ≠ "different bug found". It mean "this subset tell me nothing" → discard subset, keep searching. If counted FAIL, ddmin would minimize toward syntax error instead of target bug.

**UNRESOLVED** is a clever idea.
verdict is the practical genius. Chop a SQL query in half and you
usually get a syntax error: that is not the crash you are hunting,
and counting it as FAIL would send the search chasing the wrong
bug. So the test harness compares the **crash signature** —
exception type *and* message, or the stack location — against the
original, and anything else is UNRESOLVED: discard, keep searching.
Recognize this: it is the oracle problem ([week two](w2.md)) inside
the debugger. Delta debugging's oracle is cheap because it only has
to answer "same failure?" — never "correct output?"

### 4.3 Worked example: 847 characters to 31

The class demo, from a grammar-generated query
([deeper testing](w5.md) built such generators) that crashed a SQL
server at `query_parser.c:1247`:

| Step | Probe | Verdict | Keep |
|---|---|---|---|
| 0 | full 847-char query | FAIL | 847 chars |
| 1 | remove first half | UNRESOLVED (syntax: WHERE without FROM) | — |
| 2 | remove second half | **FAIL — same signature** | 423 chars |
| 3 | remove first half of that | UNRESOLVED | — |
| 4 | remove second half | PASS (no crash) | — |
| 5 | neither half fails alone → n=4, try quarters | UNRESOLVED ×2 | — |
| 6–14 | quarters, eighths; the WHERE clause keeps surviving | ... | 54 → 35 chars |
| 15 | `SELECT * FROM users WHERE 1=1` | FAIL | **31 chars** |

Fifteen probes, ~5 seconds each: under two minutes of machine time,
**96% reduction**, zero human reading. And the minimal input is the
diagnosis: the server crashes on the tautology `1=1` — a trivial
constant-folding path nobody tested. The bug went from "weird giant
query, probably unrealistic, low priority" to "our parser crashes
on `WHERE 1=1`, drop everything."

War story, from the first time your lecturer met this algorithm:
Zeller's paper shrank an 896-line web page that crashed Mozilla to a
single `<SELECT>` tag. Reviewers called the technique too simple to
publish. Then an overnight run at Microsoft found short SQL strings
that crashed their server. Simple scaled.

### 4.4 The same move, pointed elsewhere

ddmin is a *schema* — "binary-search anything, keeping the failure
alive" — and every instantiation is a tool you already have:

- **Inputs** — the classic, above. Pairs naturally with the fuzzers
  and grammar-based generators of [deeper testing](w5.md):
  generation finds ugly failing inputs by the thousand; ddmin makes
  each one readable. McKeeman's differential testing of C compilers
  ([week seven](w7.md)) ran exactly this pipeline: generate random
  programs, diff compilers, shrink the disagreements.
- **Versions: `git bisect`** — the input being searched is *the
  commit history*. Mark a good commit and a bad one; git checks out
  the midpoint; you run the test; `git bisect good|bad`; repeat.
  log₂(n) probes to the **failure-inducing commit**: a thousand
  commits, ten tests. On your inherited repo this is the single
  highest-value tool of the night, because the guilty commit comes
  with a message, a diff, and an author to ask — archaeology
  (last week's §3.2) with a search algorithm driving. Automate it
  with `git bisect run cmd` where cmd's exit code is the oracle —
  and notice that is the same exit-code contract your CI badge
  runs on ([week two](w2.md)).
- **Configurations** — your inherited repo's 38 knobs
  ([maintenance week](n10.md)): the failure appears with the
  customer's config and not the default. ddmin over the *settings
  diff* finds the failure-inducing option subset — often one or
  two knobs out of dozens, and the config-abyss problem shrinks to
  a readable sentence.
- **Test-order flakiness** — a test fails in the full suite, passes
  alone: ddmin over the *list of preceding tests* isolates the
  state-leaking pair. The flaky-test policy from
  [deeper testing](w5.md) said quarantine-then-diagnose; this is
  the diagnose step, mechanized.
- **Thread schedules, program slices** — the research editions
  (DejaVu-style replay; dynamic slicing) — same schema, pricier
  oracles.

One caveat before you worship: ddmin assumes failures are roughly
**monotonic** (supersets of a failing set keep failing) and
chunk-independent. Real inputs with paired structure (brackets,
quotes) generate mostly UNRESOLVED probes and shrink slowly —
which is why structure-aware shrinkers (hierarchical delta
debugging, C-Reduce for C programs; the shrinkers built into
property-based testing tools, [week two](w2.md)) shrink the *tree*,
not the string. Same idea, grammar attached.

## 5. Locate: spectrum-based fault localization

### 5.1 The idea: suspicion by attendance

You now hold a minimal failing test, plus the passing suite. Next
question: **which line is guilty?**

<img src="https://raw.githubusercontent.com/txt/se26f/refs/heads/main/etc/img/sbfl-view.png" width="95%">

The picture above (drawn in the style of Jones, Harrold & Stasko's
original Tarantula display — theirs shaded every line of a real
program) is the whole idea at a glance: each thin bar is one source
line; most of the program is **dark**, never executed by any test —
no evidence either way. **Green** regions ran only in passing tests:
almost certainly innocent. **Yellow** ran in both passing and
failing tests: ambiguous. And the eye goes straight to the one small
**red** region — executed by failing tests and (almost) never by
passing ones. The display *is* the ranking: a million lines collapse
to one place to start reading. Note also what the dark majority
says: on any one failure, most of the program is instantly
irrelevant — the Saint-Louis ravines again, drawn in pixels.

Spectrum-based fault localization (SBFL) computes that coloring by
attendance counting. Instrument the program (coverage tooling already does
this — [deeper testing](w5.md)); run all tests; for every line
record *which tests visited it*. Then the heuristic: a line visited
by **many failing tests and few passing tests** smells guilty.
Suspicion formulas over four counts per line — `ef` (failing tests
that execute it), `ep` (passing tests that execute it), plus the
totals `F` and `P`:

- **Tarantula** (Jones, Harrold & Stasko, ICSE 2002 — the paper
  that launched the field, originally as a *visualization*: lines
  shaded green→red by suspicion):
  `(ef/F) / (ef/F + ep/P)`
- **Ochiai** (borrowed from biology's species-similarity measures;
  repeatedly wins the empirical bake-offs):
  `ef / sqrt(F · (ef + ep))`
- **Jaccard**: `ef / (F + ep)` — and a zoo of cousins, below.

Rank all lines by score; a human (or a repair tool — §7) inspects
from the top.

**The formula zoo.** The field spent a decade proposing variants —
Naish, Lee & Ramamohanarao (TOSEM 2011) catalogued over thirty, most
borrowed from similarity measures in biology and data mining. A
sampler, in tonight's notation (`nf = F − ef` fails that *miss* the
line; `np = P − ep` passes that miss it):

| formula | score | flavor |
|---|---|---|
| Tarantula | `(ef/F) / (ef/F + ep/P)` | normalized fail-share |
| Ochiai | `ef / √(F·(ef+ep))` | geometric mean (biology) |
| Jaccard | `ef / (F + ep)` | set overlap |
| Dice | `2ef / (F + ep)` | Jaccard, double-weighted hits |
| Russell–Rao | `ef / (F + P)` | raw hit fraction |
| Simple Matching | `(ef + np) / (F + P)` | rewards absence from passes too |
| Hamann | `(ef + np − ep − nf) / (F + P)` | agreements minus disagreements |
| Kulczynski2 | `½·(ef/F + ef/(ef+ep))` | average of two precisions |
| Ample | `\|ef/F − ep/P\|` | gap between the two rates |
| Wong1 | `ef` | just count the failures |
| Wong3 | `ef − h(ep)`, h grows slowly | failures, lightly discounted |
| Op2 (Naish) | `ef − ep/(P+1)` | failures first; passes only break ties |
| D\* (DStar, \*=2) | `ef² / (ep + nf)` | failing evidence, squared |
| Zoltar | `ef / (F + ep + 10000·nf·ep/ef)` | savage penalty for misses |
| Barinel | `1 − ep/(ep + ef)` | probabilistic (Bayesian family) |

Three things to take from the zoo, so it is wisdom rather than
trivia:

1. **They are all the same move** — reward failing-attendance,
   punish passing-attendance — differing only in how hard each
   count pushes. Wong1 is the move naked: just `ef`.
2. **Many are provably redundant.** Xie et al. (TOSEM 2013) showed
   analytically that for *ranking* (which is all that matters —
   you inspect in order), whole groups of these produce identical
   orders, and under single-fault assumptions Op2 and the D\*
   family sit in the maximal equivalence classes. A decade of
   proposals collapsed into a handful of genuinely different
   rankers — a nice desugaring ([week seven](w7.md)): thirty
   names, few primitives.
3. **The bake-off answer**: empirically (Pearson et al., ICSE
   2017, on *real* faults rather than seeded mutants) the top
   formulas are statistically hard to separate, and formula choice
   matters far less than suite quality. Pick Ochiai or Op2, stop
   shopping, spend the effort on better tests.

### 5.2 Worked example — do this one by hand

The board exercise; it will be an exam question. Program of five
statements, suite of five tests. In the table, ✓ = that test
executes that line; — = it never reaches it (e.g. t3 takes the
else-branch, so it visits L4 but not L2 or L3). Tests t4, t5 fail;
t1–t3 pass. So F=2 failing tests total, P=3 passing. Per line, ef
counts the ✓s in failing columns, ep the ✓s in passing columns.

| line | t1 ✓pass | t2 ✓pass | t3 ✓pass | t4 ✗fail | t5 ✗fail | ef | ep |
|---|---|---|---|---|---|---|---|
| L1 `read input` | ✓ | ✓ | ✓ | ✓ | ✓ | 2 | 3 |
| L2 `if x>0 branch` | ✓ | ✓ | — | ✓ | ✓ | 2 | 2 |
| L3 `discount calc` | — | ✓ | — | ✓ | ✓ | 2 | 1 |
| L4 `else branch` | — | — | ✓ | — | — | 0 | 1 |
| L5 `print result` | ✓ | ✓ | ✓ | ✓ | ✓ | 2 | 3 |

Tarantula = (ef/F) / (ef/F + ep/P), line by line — here F=2, P=3,
so the failing ratio is ef/2 and the passing ratio is ep/3:

- L1: ef=2, ep=3 → (2/2) / ((2/2)+(3/3)) = 1 / (1+1) = **0.50**
- L2: ef=2, ep=2 → (2/2) / ((2/2)+(2/3)) = 1 / 1.67 = **0.60**
- L3: ef=2, ep=1 → (2/2) / ((2/2)+(1/3)) = 1 / 1.33 = **0.75** ← top suspect
- L4: ef=0, ep=1 → (0/2) / ((0/2)+(1/3)) = 0 / 0.33 = **0.00**
- L5: ef=2, ep=3 → same as L1 = **0.50**

Ochiai agrees and sharpens: L3 = 2/√(2·3) = **0.82** vs L2 = 2/√(2·4)
= 0.71, L1 = 2/√(2·5) = 0.63. Inspect L3 first: the discount
calculation, visited by both failures and only one pass. Note what
the algorithm did *not* need: no understanding of the code, no
author memory — just attendance. That is why it works on alien
code.

### 5.3 Honest limits (also exam fodder)

- **Executed ≠ infected.** L1 and L5 are visited by every failure
  (score 0.50) but are innocent plumbing. Ubiquitous lines — main,
  logging, utilities — always score mid-table noise. Tooling
  filters them; you should too, mentally.
- **Coincidental correctness.** A passing test that *executes the
  faulty line without triggering the error* (ran the bad branch
  with lucky values) drives `ep` up and suspicion *down* — the
  fault hides behind weak tests. Sound familiar? It is the
  coverage-is-a-disjunction lesson ([patterns recap](w6.md)) and
  the assert-nothing order-controller test, now actively
  *sabotaging* localization. Mutation-strong suites
  ([deeper testing](w5.md)) are better localizers — the techniques
  compound.
- **One formula rarely dominates**; empirical studies crown Ochiai
  on average, but the real gains came from better *suites*, not
  better formulas. Garbage tests, garbage spectrum.
- **Granularity**: line-level ranking of a million-line repo is a
  long list. Practical tools rank *methods* or *files*, then let
  bug locality (next) pre-filter.

### 5.4 Predict before you localize: history as the prior

SBFL needs a failure first. But you can rank suspects *before
anything fails*, from version history alone — the
[patterns recap](w6.md) material, now operational:

- **Bugs are social animals.** The best single predictor of the
  next bug's location is the last bug's location. Programs live in
  a few ravines of their state space — "they go to Saint Louis and
  stay there" — so faults, fixes, and the next faults pile up in
  the same corners.
- **Process beats product.** Across hundreds of projects, history
  features (churn, prior fixes, author count) predict defect
  location as well as or better than anything computed from the
  code itself. Your one-line churn counter from
  [maintenance week](n10.md) §3.2 is a defect predictor with a
  pedigree.
- **You do not even need bug labels.** This one deserves its own
  subsection, below, because it keeps being true and nobody
  believes it the first time.

### 5.5 How little information do you need? (less than anyone believes)

A running theme of this course ([the architecture lecture's AI
half-hour](w4.md)): software engineering is easy to model, because
software is a deliberate attempt to be understood — we manufacture
regularity, and the regularity is minable. Here is that claim,
cashed out four times, each time with embarrassingly small inputs:

**Case 1 — Google, 2013: three numbers beat a planet of compute.**
The story in full from [the patterns recap](w6.md): 3 billion test
executions January to October, CPU exhausted, two weeks of latency
between "I pushed" and "it passed," people resigning. The fix
needed exactly three features per test — *is it new; did it fail
last time; how long since it last ran* — weighted and combined.
Result: a 50% chance the failure surfaces in the first hour. Not
code complexity, not coverage maps, not developer identity. Three
integers you can compute from the CI log alone.

**Case 2 — Krishna et al. (2017), 800+ projects: skip the labels.**
The obvious objection to defect prediction is that it needs curated
bug data — someone tagging every issue as bug/enhancement/other,
for years. Krishna et al. mined 800+ GitHub projects and asked:
what if you just count *raw issues per week* and forecast with a
standard time-series model (train on a 20-week window, predict 4
weeks out, slide, repeat)? Findings, in order of increasing
surprise: issue, bug, and enhancement streams all show stable
temporal trends; the streams are correlated; raw issue counts
forecast future bug workload; and — the kicker — **forecasts from
unlabeled issue counts were statistically as accurate as forecasts
from the curated bug history itself.** The expensive labeling
bought nothing. For your inherited repo: `git log` and the issue
tracker's timestamps are a workload forecaster, no archaeology of
labels required.

**Case 3 — Ling, Agrawal & Menzies (TSE 2022): the same trick,
checked for where it works.** Test-case prioritization strategies
were compared across open-source and closed-source (industrial)
projects. The cheap history features (recent failures, time since
last run — Case 1's features) dominate on open-source projects,
where history is long, public, and rich. On the closed-source
systems studied, with sparser and lumpier histories, diversity-based
orderings (spread the tests across different behaviors first) did
better. The meta-lesson matters more than the league table:
**minimal-information models work because of the information
environment, not magic** — before trusting the cheap predictor on
your repo, check your repo looks like the repos it was validated
on. (Your inherited proj2 has ten weeks of dense history: Case 1
conditions, roughly.)

**Case 4 — Long et al. (TSE 2024): it even works on *process*
shape.** The paper behind this course's banner figure (Long,
Drylie, Ritschel & Koschnick, *An Assessment of Rules of Thumb for
Software Phase Management*): using defense-project cost data, they
tested whether the old one-third-planning-style effort splits
([week one's](w1.md) V-diagram numbers) actually relate to
outcomes — and found that how a project *distributes effort across
phases* carries real signal about schedule success. Read together
with Cases 1–3: from a project you can know almost nothing — a few
per-test counters, unlabeled ticket counts, coarse phase fractions
— and still predict what fails soonest, where, and whether the
schedule holds. The information was always lying on the ground.

Why does so little suffice? Two reasons the course has already
built. First, bug locality (§5.4): failure mass concentrates, and
concentrated distributions are predictable from small samples.
Second, the regularity is *manufactured*: humans write software to
be comprehensible, review it into conventions, and commit it in
habits — so process traces are low-dimensional, the same reason
the per-layer LLM surrogates of [week four](w4.md) compress. The
practical rule for proj3, and for your careers: **before buying
the complex model, price the three-feature one.** It is the
compact-AI doctrine ([week one](w1.md) — "can you do it for a
penny?") applied to analytics about your own project.

Put together with §5.4: **prior × evidence**, Bayesian in spirit.
Cheap history says which files to suspect before any failure; the
spectrum (§5.1) updates that with tonight's evidence; you read
from the top of the combined list. On your inherited repo, compute
the prior in week one (you already did, if you built last week's
debt ledger) and the posterior the first time CI goes red.

## 6. Fix, verify, and keep it fixed

The loop closes only when four things are true — and the inherited
repo makes each one a named discipline from an earlier week:

1. **The fix addresses the fault, not the failure** — no clamps
   over symptoms (§2.2). You can now *say why* the failure
   happened, in a sentence, referencing the faulty line. If you
   cannot, you have suppressed, not fixed.
2. **The failing test joins the suite forever.** The minimal
   reproduction from §4 *is* the regression test — already small,
   already fast. A bug fixed without a pinning test is a bug
   scheduled for re-entry (regression suites,
   [deeper testing](w5.md)).
3. **Nothing else broke** — full suite green, and on an inherited
   repo that claim is only as strong as last week's mutation
   audit said it is.
4. **The ledger is updated** — issue closed with the cause
   written down (issue-stamping, [week two](w2.md)); if the fix
   revealed a class of similar risks ("every caller of this
   parser might double-free"), that goes in the debt ledger, and
   bug locality says you *will* be back in this file.

## 7. Repair: when the fixer is also an algorithm

### 7.1 GenProg: evolution over suspicious lines

If localization gives a ranked list and tests give a verdict, a
machine can close the loop. **GenProg** (Le Goues, Nguyen, Forrest
& Weimer, TSE 2012 — the paper that founded automated program
repair):

1. Run the suite; collect passing and failing tests.
2. **Localize**: SBFL (§5) marks suspicious statements — the
   search space is only those lines, not the program.
3. **Mutate**, genetic-programming style, inside that space:
   delete a statement; insert a statement *copied from elsewhere in
   the same program*; swap two statements.
4. **Fitness** = tests passed, weighted so the failing tests count
   extra. Crossover between promising variants; repeat for
   generations.
5. Stop at a variant passing **all** tests: a candidate patch.

Two design choices carry the insight. *Localize first* — without
§5 the search space is the whole program and evolution drowns.
*Steal, don't synthesize* — new code is copied from the same
program, betting that the needed fix already exists somewhere in
some form. That bet has a name, the **plastic surgery
hypothesis**, and mining studies back it: a large fraction of real
human fixes are rearrangements of code already present. (You met
the deeper reason last week: software is self-similar — we
manufacture regularity — so the donor-code pool is rich.)

### 7.2 The catch, and it is this course's favorite catch

GenProg's acceptance oracle is "passes all tests." But
[week two](w2.md) taught you what a test suite is: a **partial,
disjunctive** spec. So the search gleefully finds patches that
satisfy the letter of the suite and nothing else — **patch
overfitting**. The hall-of-shame patch: the failing test checks
behavior in a branch; *deleting the branch* makes the test's
precondition unreachable; suite goes green. Several early GenProg
"repairs," on re-examination, were exactly this shape — functionality
amputated, suite satisfied.

Say it in course language: **automated repair converts the oracle
problem from a testing nuisance into the whole ballgame.** The
repair is only as good as the suite is strong — which is why the
mutation-testing bar ([deeper testing](w5.md), and the PIT talk's
assertion-free test that scored 100% coverage) stops being hygiene
and becomes the safety spec for the repair robot. Weak suite + APR
= an optimizer searching for the cheapest way to lie to you.

And — scientific integrity moment — the sharpest version of this
critique came from **GenProg's own author**. Claire Le Goues
co-wrote the paper that put the knife in:
[*Is the Cure Worse than the Disease? Overfitting in Automated
Program Repair*](https://doi.org/10.1145/2786805.2786825)
(Smith, Barr, Le Goues & Brun, ESEC/FSE 2015 — same conference,
same year as the knobs paper). The experimental design is the
train/test split you know from [week one](w1.md): repair bugs
using one test suite, then grade the patches on an **independent
held-out suite** the search never saw, with human-written patches
as the control. Findings: plausible patches routinely failed the
held-out tests — passing the repair suite did not generalize —
and **patch quality tracked the coverage of the repair suite**:
better fences, better repairs. The human patches generalized;
the generated ones overfit. Four years later, surveying the field
in CACM
([Le Goues, Pradel & Roychoudhury, *Automated Program Repair*,
2019](https://cacm.acm.org/research/automated-program-repair/)),
she and her co-authors named **weak specifications as the grand
challenge of the whole field**: repair is driven by test suites
because real specs do not exist, so patches may "not generalize to
tests outside the test-suite." Note what happened there, because
it is this course's ethics lecture in miniature: the inventor
published the strongest attack on her own invention, and the field
got honest — reported fix rates dropped, evaluation standards
rose. Failures are findings, practiced at career scale.

The defenses, each one a course concept doing new work:

- **Held-out tests the search never sees.** Split your tests into
  two suites. The repair tool runs against suite one, over and
  over, until its patch goes green. Then — once, at the end —
  suite two judges the patch. Because the search never saw suite
  two, it could not tune the patch to suite two's blind spots, so
  suite two's verdict measures the patch, not the search. This is
  the train/test split from [week one's](w1.md) label-leak story:
  grade an optimizer on the data it optimized against and you get
  its score, not reality. Where does suite two come from? Reserve
  some existing tests; or write fresh ones for the patched
  behavior; or use metamorphic relations
  ([deeper testing](w5.md)) — "adding a filter cannot increase the
  count" — which work well here precisely because the repair tool
  was never shown them, so a patch that fakes its way past suite
  one still has to survive checks it never trained on.
- **Strengthen the suite *before* enabling the robot.** The
  Cure/Disease coverage result makes this quantitative: repair
  quality rose with repair-suite coverage, so every mutation-audit
  hour from [maintenance week](n10.md) is now *safety engineering*
  for the repair loop, not hygiene. Corollary with teeth: on an
  inherited repo whose suite you have not audited, APR is not yet
  safe to switch on — you do not know what the optimizer can get
  away with.
- **Prefer minimal patches, and diff them against the fault.** A
  correct fix is usually small and *explains the failure* (§6's
  rule: you can say why, in a sentence, naming the faulty line).
  An overfit patch usually smells: it deletes code, adds
  special-case guards shaped exactly like the failing test's
  inputs, or edits far from any localized line. Reviewing a patch
  is hypothesis-testing (§2) where the patch is the hypothesis —
  demand it predict something beyond the tests it passed.
- **Human review of every candidate, with the human owning it.**
  Bainbridge again ([week one](w1.md)): the robot does the easy
  patches, so the human reviewer must stay sharp enough for the
  hard ones — and "it's my code" applies to merged patches whoever
  wrote them. Review the diff, not the green checkmark: the
  checkmark is the thing the optimizer was paid to produce.

### 7.3 LLM repair: 2026 status

The first LLM wave (2022–23) replaced GenProg's mutate-and-pray
with a single prompt — "here is the failing test, the trace, and
the suspicious region; write a patch" — and immediately fixed more
single-function bugs than a decade of genetic search. But that is
no longer the state of the art. Notes on where the field actually
is:

- **The benchmark changed the game.** SWE-bench (Jimenez et al.,
  ICLR 2024) reframed repair as *repository-level issue
  resolution*: real GitHub issues from real Python projects, and a
  patch counts only if it passes **held-out tests the model never
  sees** — the field adopted the Cure/Disease defense (§7.2) as
  its standard scoring rule. SWE-bench Verified is the
  human-audited 500-issue subset everyone now quotes.
- **Two architectures fought: agents vs pipelines.** Agentic
  systems (SWE-agent; AutoCodeRover, ISSTA 2024) give the model
  tools — open files, search, run tests — and let it decide what
  to do next, step by step. Then **Agentless** (Xia et al., FSE
  2025) stripped the autonomy out: a fixed three-phase pipeline —
  hierarchical **localization** (narrow repo → files → functions),
  then **repair** (generate candidate patches), then
  **validation** (run the tests, pick the survivor) — and beat
  the contemporary open-source agents at a fraction of the cost
  (tens of cents per bug). Look at those three phases again: that
  is *this lecture* — §5, §7, §6 — run by a machine. The field
  rediscovered that structure beats improvisation, which is the
  write-the-loop-not-the-prompt lesson arriving in
  [next week's](w7.md) agentic-coding material.
- **The 2026 numbers.** Frontier models inside thin agent
  harnesses now resolve on the order of **95% of SWE-bench
  Verified** — up from ~2% for the best systems of 2023. Three
  years, two orders of magnitude.
- **Read those numbers like an engineer, not a fan.** The
  caveats are all course concepts. *Contamination*: these public
  repos are in training data — the label-leak worry
  ([week one](w1.md)) at benchmark scale. *Selection*: Verified
  is curated, Python-only, mostly small patches; your inherited
  repo is none of those. *And the oracle is still tests*: 2026
  studies auditing the accepted patches find some pass validation
  without the validating tests ever exercising the bug — patch
  overfitting, alive inside a 95% score. The leaderboard measures
  "passes the held-out suite," which is the best cheap oracle we
  have and still not the same thing as "correct."

So the honest 2026 summary: the generator improved beyond
recognition; the certifier did not. Walk that logic through:

1. **How a repair tool gets graded has not changed.** GenProg in
   2012 and an LLM in 2026 both declare victory the same way: "all
   tests pass." The judge is still the test suite.
2. **So the old failure mode carries over.** Patch overfitting was
   never a property of genetic programming — it is a property of
   the *judge*. Any optimizer paid to make tests green will find
   the cheapest green, and if the suite is weak, the cheapest
   green can be a wrong patch. Swap the patch-generator, keep the
   judge, keep the disease.
3. **And the LLM version is more dangerous, not less.** GenProg's
   overfit patches looked like garbage — randomly deleted
   statements, obviously mangled code; a reviewer smelled them
   instantly. An LLM's overfit patch is fluent: well-named
   variables, a plausible comment, idiomatic style. It *reads*
   like a real fix while doing the same cheap thing. The surface
   quality went up; the correctness guarantee did not.
4. **Which is week one's hallucination lesson, relocated.** LLMs
   are optimized to produce *plausible* output, and
   plausible-but-wrong is exactly what slips past a human skim. So
   as the generator gets better at plausibility, the weak-suite
   risk shifts from "obvious junk patch rejected at review" to
   "convincing wrong patch merged."

In one sentence: LLMs improved the patches' looks, not the oracle
that certifies them — so with a weak suite you now get wrong
answers that are harder to spot. The agent-era version of the trap
is already in your own history: the [architecture
lecture's](w4.md) model that "fixed" things by quietly rewriting
the kernel its owner relied on. Same machinery you will use in
proj3; same defenses as §7.2, with verdicts
([week one](w1.md)) on every repair run.

So the human job shifts exactly as Bainbridge predicted
([week one](w1.md)): less writing of patches, more **judging** of
patches. Judging needs §5's evidence and §2's hypothesis
discipline. The algorithms localize and propose; you remain the
oracle of last resort.

### 7.4 Debug the modeling, not just the code

One widening move before the mechanics end. Sometimes the fault is
not in any line of code. It is in the *shape* of the system: two
components make demands that cannot both be true. No amount of
line-reading finds that, because every line is fine.

The classic arena is package management. Every package declares
rules: "I need library X version 2 or higher"; "I conflict with
package Y." Install enough packages and the rules collide. **Opium**
(Tucker, Shuffelton, Jhala & Lerner, ICSE 2007) treated this as a
logic problem. Write every rule as a constraint. Hand the
constraints to a SAT solver — a program that answers "is there any
assignment that satisfies all of these?" If the answer is no, your
install is impossible, and the solver can name the clashing rules.
If the answer is yes, go further: among all the valid
installations, ask an optimizer for the *cheapest* one — fewest
packages changed. And if the user hates the proposed answer, add
their objection as one more constraint ("not that configuration")
and solve again. Each round of dislike narrows the space; the
solver does all the searching. The same machinery runs at absurd
scale: the Linux kernel's build configuration has thousands of
features and hundreds of thousands of rules about which features
can coexist, and "is this configuration even buildable?" is answered
the same way — as a SAT query.

Now put this section beside §7.1 and see one shape twice. GenProg
repairs code: its search space is edits, and its oracle is a test
suite. Opium repairs configurations: its search space is package
choices, and its oracle is a set of logical rules. Both are
**repair as search against an oracle** — only the space and the
judge change.

The proj3 payoff: when your inherited repo will not install —
two dependencies each pin a different version of some third
library — stop reading code. There is no faulty line. Write the
version rules down explicitly, see which ones contradict, and
decide which rule to relax. Writing the constraints down *is* the
debugging; the moment they are explicit, the contradiction is
visible, and often no solver is even needed.

- **SBFL bake-offs**: large empirical comparisons across formula

  combined evidence beats any single source — the prior×evidence
  framing of §5.4 is where the field landed.

  overfitting papers, APR evaluation moved to held-out
  correctness checks and human audits of patch semantics; reported
