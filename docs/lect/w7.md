## 1. Glossary

### 1.1 Weird theory, real money

- **Logic programming → telecoms** — Erlang (Ericsson, 1986) borrowed its syntax
  from Prolog, and its first interpreter was written in Prolog. Its selling point
  is the *process*: an Erlang process starts at a few hundred words of memory
  (an OS thread wants KBs to MBs). So one machine can hold millions of phone calls,
  each a process that is created, used, and forgotten.
- **WhatsApp** — written in Erlang. Facebook bought it in 2014 for about $19B
  (about $22B at close). At purchase, a few dozen engineers ran it for hundreds of
  millions of users. Moral: odd theory turns into industrial reality.
  (Class said Microsoft, 2019, Elixir; the record says Facebook, 2014, Erlang.
  Elixir is a newer language on the same Erlang VM.)
- **Desugaring** — a compiler step. Big friendly constructs (classes, `while`,
  `if`) are rewritten into a few tiny ones. Humans like the top layer; machines
  and optimizers like the bottom layer, because it is small and uniform.
  > Easy to use up here. Easy to implement down there. Sugar in between.

### 1.2 The 1945 machine, again

- **von Neumann, the man** — also a weapons scientist: implosion lenses for the
  first plutonium bomb, and the maths of air bursts. In 1953–54 he chaired the
  committee that told the Eisenhower administration that lighter H-bombs made
  ICBMs practical. (Class said "Truman, 1958"; von Neumann died in 1957.)
- **Tail-call optimization (TCO)** — if a function's *last* act is to call
  something and return its result, the caller's frame is no longer needed, so the
  callee can reuse it. A recursive loop then runs in one frame. Python has no TCO;
  its default limit is 1000 frames (`sys.getrecursionlimit()`).
- **Dataflow machine** — the alternative to "fetch the next instruction". Each
  operation waits by its input "puddles". When every input has a value, it fires
  and writes to its output puddle. Order comes from the data, not from a program
  counter. Every node can run at once, so it is natural for parallel and
  cloud work.
  > Why should you fetch the next data? Why shouldn't it find you?

### 1.3 Delays

- **Strict (eager) evaluation** — all arguments are computed *before* the call.
  That is why `if` cannot be an ordinary function in Python:
  ```python
  def my_if(c, then, else_): return then if c else else_
  my_if(x == 0, 0, 1 / x)              # crashes at x=0: both branches ran
  my_if(x == 0, lambda: 0, lambda: 1 / x)()   # thunks: only one runs
  ```
- **Delay** — timm's plain word for a thunk. A program is a table of delays.
  Only the delays that execution wanders into ever wake up.
- **Lambda calculus, why "calculus"?** — from a student question. "Calculus"
  is Latin for a pebble used to count. In logic, it means any formal system of
  rules for pushing symbols (as in "predicate calculus"). It has nothing to do
  with derivatives.
- **Fuzzy logic as lambdas** — also from Q&A. Fuzzy sets have soft borders
  ("old" is 0.2 true at 50). To build it, you pass membership *functions*
  around, and AND/OR/NOT become functions over functions. Same mechanism.
- **Ship the thunk, not the JSON** — two cloud agents can swap work as bodies,
  not as data dumps. The receiver runs the body *inside its own firewall*, checks
  what came out, and returns only what policy allows. (Price: you now run
  someone else's code. That needs a sandbox, or capability limits.)

### 1.4 Streams are everywhere

- **File stream** — "while not end of file, read the next line" is a generator.
  The 10 GB file never fits in RAM; you hold one record at a time.
- **`range`** — Python 3 does not build a list. `range(1, 10**6, 1000)` is a small
  object that computes each value on request.
- **`yield` vs `return`** — `return`: the café is closed, here is what we have.
  `yield`: here is one thing, and I will wait, ready to go on.
- **Recursion needs TCO** — the five-line `each` in the notes calls itself once
  per item. In Lisp, Lua, or Scheme that is a loop. In Python it dies near
  item 1000.

### 1.5 Closures are the bigger idea

- **Closure** — a function plus a bag of the variables that were live when it
  was made.
- **The car factory** — permits, building, and hiring happen *once*, before the
  function is returned. After that, each call makes one car, and the factory
  travels inside the closure. (Same move: sort the cats and dogs once, then hand
  back a sampler that remembers the sort.)
- **Objects ⊂ closures** — a closure can hold data *and* functions. That is an
  object. OO is one small corner of what closures can do.
- **Python and lambda** — in 2005 Guido van Rossum planned to drop `lambda`,
  `map`, and `filter` in Python 3. After pushback, `lambda` stayed (one
  expression only), and `reduce` moved to `functools`.
- **Java** — anonymous inner classes were Java's stand-in for lambdas until
  Java 8 (2014) added real ones.

### 1.6 Bodies on the move: the catalogue, spoken

- **GUI callback** — the GUI knows windows and checkboxes, not employees or cars.
  The model gives it a check function. The same GUI then serves a payroll app on
  Monday and a car app on Tuesday.
- **The handbag** — timm's word for a Strategy or Visitor payload. One walker
  carries the bag past every item. The bag decides what to keep: names, health
  records, the 20 events (out of 7000 processes) that matter. A bag can also
  *compute*, e.g. drop a low-priority item when a better one comes.
- **The oops handbag** — a transaction sends a work bag and an undo bag. If any
  step fails, the undo bag runs back over what was done and cleans up.
- **Undo stack** — every edit pushes its inverse, as a lambda. Ctrl-Z pops and
  runs one. A 20-level undo is a circular buffer of 20 lambdas: edit 21
  overwrites edit 1.
- **Event-driven, desugared** — a queue of bodies. Add a priority to each, so
  memory events run before GUI events, and it is a priority queue of bodies.
- **Shell pipes** — `ls | wc` is composition of stream filters. Same idea at
  the OS level.
- **Log, don't print** — a logging wrapper is generic: get the name, call it,
  catch the output, write it to the log. Production code has logs with
  priority levels, not `print`s you comment out.
- **Timsort** — Python's sort (Tim Peters, 2002). It is *not* "quicksort with two
  pivots" (that is Java's dual-pivot quicksort for primitives). Timsort is a
  merge sort plus insertion sort that finds runs that are already sorted in the
  data. The point stands: an engine this tuned should be closed to edits and open
  to behavior, via `key=`.
- **CLU** — Barbara Liskov's language (MIT, mid-1970s). It gave us iterators
  (with `yield`), exceptions, and abstract data types. The idea: the internals are
  too complex to know, so pass in something that gets carried around.

### 1.7 Desugaring as a research method

- **Desugar the skills** — given 12 skills for a domain, build skill one from
  primitives. Skill two reuses some of those; skill three reuses more. Code per
  skill falls.
- **The LLM version** — ask an LLM for each skill alone and you often get a
  thousand lines of glue per skill, and a maintenance nightmare.
  > The next new thing on the list? "I have seen that before."

### 1.8 Testing coda

- **Oracle problem** — you can run a program a million times, but who says which
  outputs are right? Most clever test methods are ways around this.
- **Delta debugging** (Andreas Zeller, ~2002) — take a failing input and keep
  cutting it: split it into chunks, test the pieces and their complements, and
  keep any smaller input that still fails. It ends with an input where removing
  any one piece makes the bug go away (*1-minimal*). No domain knowledge needed.
  Classic case: an 896-line web page that crashed Mozilla shrank to one `<SELECT>`
  tag. timm's story: reviewers called it too simple to publish; a night run at
  Microsoft found short SQL strings that crashed their server.
- **Mutation testing** (recap) — break the code on purpose. If the tests stay
  green, they cannot tell right from wrong, so extend them.
- **Differential testing** (McKeeman, 1998) — the same spec built many times
  (SQL engines, JavaScript engines, C compilers). Run the same input through all.
  Seven say A, one says B: look at the one. The other builds are the oracle.
- **The cost** — all three burn CPU.
  > You kiss a lot of frogs before you find your broken princess.

## 2. Review questions

Seven questions. **(a)** low Bloom (recall, ~2 min). **(b)** high Bloom (analyse
or apply, ~4 min). Answers are in section 3.

**1. Strict evaluation**
(a) Define strict (eager) evaluation and define a thunk.
(b) A student writes `def my_if(c, t, e): return t if c else e` and calls
`my_if(n == 0, 0, total / n)`. It crashes when `n` is 0. Explain why, and show
the change that fixes it using thunks.

**2. Dataflow vs von Neumann**
(a) In one sentence each, say what decides the next step in a von Neumann
machine and in a dataflow machine.
(b) Explain why dataflow suits a cloud of many workers better than one central
controller does.

**3. Tail calls**
(a) Define tail-call optimization.
(b) A recursive walk over a 100,000-line file works in Lua but fails in Python.
Explain the cause in terms of stack frames.

**4. Closures and objects**
(a) Define a closure, name its two parts, and say which part holds the car
factory's permits, building, and hiring.
(b) Write a Python `counter(start)` that returns `{"inc": ..., "get": ...}`:
two closures over one shared, hidden count. Then name the two OO features this
gives you for free, and the one OO feature it does not give you.

**5. Undo as data**
(a) Describe an undo stack in terms of lambdas, and how a fixed 20-level undo is
kept in fixed memory.
(b) A drawing app stores a full copy of the canvas after every edit, to support
undo. Explain why storing inverse operations (lambdas) instead scales better.

**6. Shipping bodies across a boundary**
(a) State one benefit of sending a thunk, instead of JSON data, to a remote agent.
(b) Explain the main risk for the receiver, and one control that reduces it.

**7. Oracles**
(a) Define the oracle problem. Name the oracle Schemathesis uses by default.
(b) Choose delta debugging, mutation testing, or differential testing for this
task, and justify the choice: "we have three SQL engines and no expected outputs
for 10,000 random queries."

## 3. Answers, briefly

**A1.** (a) Strict evaluation computes every argument before the function body
runs. A thunk is a zero-argument function that holds work until it is called.
(b) `total / n` is computed on the argument line, before `my_if` runs, so it
divides by zero even though that branch is never chosen. Fix: pass
`lambda: 0` and `lambda: total / n`, and have `my_if` call only the chosen one:
`return t() if c else e()`.

**A2.** (a) von Neumann: a program counter says which instruction is next.
Dataflow: an operation runs as soon as all of its inputs are present.
(b) Each worker only needs its own inputs, so no one schedules anyone. Work runs
in parallel wherever data is ready, and there is no single controller to become
the bottleneck or to fail.

**A3.** (a) When a function's last action is a call whose result it returns, the
runtime reuses the current frame instead of pushing a new one. (b) Each
recursive call in Python pushes a new frame, and Python has no TCO, so near
1000 frames it raises `RecursionError`. Lua does TCO, so the same recursion
runs in one frame.

**A4.** (a) A closure is a function plus the variables captured from the scope
where it was created. Two parts: the body (code) and the captured environment
(data). Permits, building, and hiring are the environment: paid for once, before
the function is handed back. (b)
```python
def counter(start):
  n = start                                  # hidden, shared
  def inc(k=1):
    nonlocal n; n += k; return n
  return {"inc": inc, "get": lambda: n}
c = counter(10); c["inc"](); c["get"]()      # -> 11
```
Free: state (`n` lives between calls) and encapsulation (nothing outside can
touch `n`; no `_n` convention needed). Missing: inheritance -- no class to
subclass, so sharing between counters means writing it by hand.

**A5.** (a) Each edit pushes a lambda that reverses it; Ctrl-Z pops and runs the
top one. A circular buffer of 20 slots holds the last 20; edit 21 overwrites the
oldest. (b) A canvas copy costs the whole image per edit. An inverse costs only
the size of the change ("remove stroke 41"), so memory grows with what changed,
not with canvas size.

**A6.** (a) Any one of: the receiver runs it inside its own firewall and returns
only what policy allows; no format to design, write, and parse on both sides;
the logic travels with the request. (b) The receiver runs code it did not write,
which might read or damage things. Controls: a sandbox, or capability limits
(the body gets access only to what it is handed).

**A7.** (a) The oracle problem: for many inputs we cannot say what the right
output is, so we cannot judge a test run. Schemathesis's default oracle is
generic: no server errors, and responses match the declared schema and status
codes. (b) Differential testing. The three engines implement one spec, so they
act as each other's oracle: any query where one engine disagrees is a lead.
Delta debugging needs a known failure first, and mutation testing grades a test
suite, which you do not have.
