# N6: Patterns + Code Quality

**Links:** [Home](../../README.md) · [Project 2](../submit/project.md) ·
[In-class exercise](n06ex.md) · [N4 architecture](n04.md)

Build month, week one. N4 gave you the big shapes (layered,
event-driven, microkernel...) and the four undercurrents (coupling,
cohesion, information hiding, design-for-test). Tonight is the
scale below architecture: the pattern you reach for inside a
module, the smell that tells you a module is rotting, and the
refactoring moves that fix it — plus the discipline of knowing when
a pattern is NOT earning its keep.

One hour of lecture (talks take the other hour); the research
corner and the [closures supplement](closures.md) are READ AT HOME
— examinable, not spoken.

The 2026 twist, again: LLMs know every pattern ever named, and will
deploy all of them on a three-line problem if you let them. Pattern
literacy used to be about knowing the recipes. Now it is about
recognizing when your code — or your agent's code — is wearing a
costume it does not need.

## 0. One spec, three systems (the Shaw move) (10 min) ▪▪▪▪

Mary Shaw and David Garlan, who founded software architecture as a
field, made one point above all: **no design is best; every design
is a purchase.** Their classic demonstration: take ONE spec — a
mobile robot (sense the world, plan a path, act, don't fall down
stairs) — and derive rival systems from rival trade-offs:

| you weight... | you derive... | you pay... |
|---|---|---|
| simplicity, predictability | control loop (sense→plan→act, round and round) | sluggish response; surprises mid-plan are ignored |
| safety isolation, changeability | layered (reflexes low, goals high) | latency through the stack; tasks that span layers hurt |
| resilience, add-a-sensor-anytime | blackboard (modules read/write shared state) | synchronization cost; nondeterminism; testing pain |

Same requirements. Three defensible robots. The columns decide, not
the fashion. Tonight's [exercise](n06ex.md) makes you do this move
on the food-delivery domain you already know — one trade-off sheet,
and from it your team derives and defends a design, with an LLM as
sparring partner. Shaw's book, but the table argues back.

Hold that mindset for the whole night: every pattern below is a
small purchase. Plus column, minus column, receipt.

## 1. The map: 23 patterns, three families (5 min) ▪▪

A design pattern is a named, reusable move — smaller than an
architecture, bigger than a function. The lineage: Christopher
Alexander noticed that good BUILDINGS repeat solutions ("A Pattern
Language", 1977 — courtyards, window seats, entrance transitions);
the Gang of Four (Gamma, Helm, Johnson, Vlissides, 1994) did the
same for object-oriented code and cataloged 23, in three families:

```
Design Patterns (23)
    │
    ├─ Creational (5) ──── how objects get MADE
    │    Factory · Abstract Factory · Builder ·
    │    Prototype · Singleton
    │
    ├─ Structural (7) ──── how objects COMPOSE
    │    Adapter · Facade · Decorator · Proxy ·
    │    Composite · Bridge · Flyweight
    │
    └─ Behavioral (11) ─── how objects INTERACT
         Strategy · Observer · Template Method · Visitor ·
         Iterator · Command · State · Chain of Responsibility ·
         Mediator · Memento · Interpreter
```

Each pattern is a tiny object model — a few classes in a fixed
dance:

<img width="700" alt="the Gang-of-Four pattern library: each pattern as a small class diagram" src="../../etc/img/n06-patterns.jpg">

Do not memorize the diagram. Its enduring value is VOCABULARY:
"wrap it in an Adapter" transmits a whole design in four words, in
code review, in interviews, and — new in this decade — in prompts:
pattern names are the words your LLM listens to most reliably,
because it read the same catalog everyone else did.

One more map-note before the tour: Norvig (1996) showed that 16 of
the 23 become invisible or dramatically simpler in dynamic
languages. A pattern is often a WORKAROUND FOR A MISSING LANGUAGE
FEATURE: Iterator became Python's `for`; Strategy became a lambda;
Decorator became `@`. The [closures supplement](closures.md) walks
that collapse in detail. Moral: patterns are truths about design
pressure, not truths about class diagrams.

## 2. Six patterns that earn their keep (25 min) ▪▪▪▪▪▪▪▪▪▪

Of the 23, you need about six — and you have already met most of
them wearing work clothes. Each below: the idea, the Python, the
purchase.

**Strategy** — behavior passed in as a value. `sorted(key=...)` is
Strategy; so was N3's bar-scenario glass that knows how to pour
itself:

```python
def total(cart, pricing):              # pricing IS the strategy
    return sum(pricing(item) for item in cart)

happy_hour = lambda item: item.price * 0.5
surge      = lambda item: item.price * 1.3
total(cart, happy_hour)                # total() never changes
```

Buy when variants multiply (pricing rules change weekly, G4!); the
minus is one more indirection between reader and behavior.

**Observer** — the pattern inside every event system (N4): parts
announce, subscribers react, nobody calls anybody:

```python
subscribers = []
def order_changed(order):
    for fn in subscribers: fn(order)

subscribers.append(notify_courier)     # each learns of changes
subscribers.append(notify_customer)    # neither knows the others
```

Buys decoupling; costs debuggability (remember N4's twice-firing
handler and the correlation-ID scar: who called this? Nobody —
that is the point, and the pain).

**Adapter** — a shim that makes an alien interface look native.
The pattern of integration week:

```python
class StripeAdapter:                   # alien API, native face
    def __init__(self, stripe): self.s = stripe
    def charge(self, dollars):
        return self.s.PaymentIntent.create(
                 amount=int(dollars*100), currency="usd")

# checkout says gateway.charge(10.99) -- and only the adapter
# knows which vendor is behind the wall
```

Wrap the gateway once and a vendor swap changes the shim, not
forty call sites (and Mars Climate Orbiter whispers: the adapter
is WHERE the unit conversion lives, written down, once). Minus:
shims accrete; a shim on a shim is a smell.

**Facade** — one simple front door hiding an ugly subsystem:

```python
class Orders:                          # the front door
    def place(self, cart, card):
        self._validate(cart)           # three subsystems,
        self._charge(card, self._price(cart))  # invisible
        self._dispatch(cart)
```

Your proj2 "framework others extend" wants exactly this: the next
team calls `place()` and never reads your internals (Parnas, N4,
again). Minus: facades rot into god classes — the door grows a
kitchen.

**Factory** — construction behind a function, so callers never
name the concrete class:

```python
def payment(kind):
    return {"card":    CardPayment,
            "cash":    CashPayment,
            "credits": SiteCredit}[kind]()   # data decides

pay = payment(order.method)            # caller knows no classes
```

Buys swap-ability (add ApplePay = add one dict row); costs a layer
of "where is this actually made?"

**Decorator** — wrap a thing with a same-shaped thing that adds a
feature. Python gave the pattern syntax:

```python
def retry(fn):
    def wrapped(*args):
        for _ in range(3):
            try: return fn(*args)
            except TransientError: pass
        raise
    return wrapped

@retry                                 # charge, now with retry;
def charge(card, cents): ...           # charge's code unchanged
```

Logging, caching, auth, retry — all cross-cutting features that
never touch the wrapped function. (And note what `retry` is: a
closure. The supplement was not optional theory.) Minus: five
nested wrappers make stack traces archaeology.

And one warning by name: **Singleton** — a global variable with a
diploma. The GoF pattern most cited in industry AND most regretted:
it couples everything to one hidden instance and makes tests fight
over shared state. Config objects passed in beat singletons nearly
always (design-for-test, N4).

**Rule for all six**: a pattern is justified by the CHANGE it
absorbs, not by existing. "We used Strategy" is not a design
rationale; "pricing rules change weekly, so pricing is a Strategy"
is.

## 3. Code smells: the vocabulary of rot (10 min) ▪▪▪▪

A smell is not a bug — it compiles, it passes tests. It is a
structure that makes the NEXT change expensive. The classics:

- **God class** (the Blob): one class doing everything — N3's
  bartender who pours, charges, tallies and reorders. Diagnosis:
  describe the class in one sentence without "and". The cure is
  never "split into GodClass1 and GodClass2" — push each
  responsibility to the object that owns the data (glass pours,
  till counts).
- **Dead object**: the other end of the same smell — a class that
  is just data, with all its verbs stolen by the god.
- **Long message chain**: `order.customer().address().city()` —
  a train wreck; one refactor anywhere derails every caller.
- **Duplicated code**: the smell LLMs mass-produce. Same logic,
  three files, and a bug fix that must be found three times. (The
  aislop evidence from N1: AI-heavy repos show measurably more
  copy-paste and churn. Cheap to write is not cheap to own.)
- **Lava flow**: dead code nobody dares delete — "maybe something
  uses it." Version control is your courage: delete it; git
  remembers.
- **Golden hammer / pattern fever**: applying the beloved tool to
  every problem. The LLM-era version is instant: ask for a TODO app
  and receive AbstractTaskFactoryProvider. YAGNI — you aren't
  gonna need it — is the counter-spell: build for today's
  requirement, refactor when the second requirement ARRIVES.

Metrics can watch for smells at scale — big class, many methods,
low cohesion of a class's parts, deep inheritance — and your proj2
CI can run a linter that flags the worst. But treat thresholds the
way N3 treated NFR numbers: a tripwire for a human look, not a
verdict.

## 4. Refactoring: paying the debt down (10 min) ▪▪▪▪

Refactoring = changing structure without changing behavior. The
discipline, not the vibe:

1. **Green first.** Refactor only under passing tests (N2's
   red-green-REFACTOR; the refactor step finally gets its night).
2. **Small named moves**: extract function; rename; move method to
   the data it uses; replace conditional with polymorphism (that is
   how the bartender's if-ladder became pouring glasses); inline
   the needless indirection (refactoring runs BOTH directions).
3. **One move per commit.** A commit titled "refactor + fix + new
   feature" is three commits wearing a trench coat, and reverting
   it is surgery.
4. **Verify behavior held.** Your differential move from N5: same
   inputs through old and new, diff the outputs. Tests green +
   diff empty = refactor proven, cheaply.

When? The rule of three: first time, write it; second time, wince
and copy; third time, refactor. Debt metaphor honestly used: some
debt is GOOD (ship the demo, learn the market) — the sin is not
borrowing, it is not tracking the loan. Keep a DEBT.md; the proj2
rubric reads it as engineering, not confession.

**Agent-era coda**: refactoring is what keeps LLM code maintainable
by humans, and the safety rules are identical for human and agent:
tests before, small steps, diff after. An agent refactoring without
a safety net is a lava-flow generator with excellent manners.

## 5. Research corner: does any of this matter, measurably? (READ AT HOME)

Three honest data points. (1) Refactoring studies show
structure metrics improve while defect rates move less than
advocates hope — structure buys CHANGE SPEED more than it buys
correctness. (2) The Ling-style lesson generalizes: quality
policies are context-dependent; thresholds imported from another
org mislead. (3) Long et al. (TSE 2023) — the figure on the course
README — maintainability correlates with survival: systems that
stay changeable stay alive. Quality is not polish; it is life
expectancy.
