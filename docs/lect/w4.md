## 1. Glossary

### 1.1 What architecture is for

- **Architectural pattern** — reusable wisdom about structure: how
  to split a system into parts, and how the parts talk. Each
  pattern solves a class of problems and bills you later.
- **The skill** — not knowing the patterns. Knowing when NOT to use
  one.
- **The working definition** *(lecture)* — a good architecture lets
  you work alone at least half the time. It tells you what is
  yours, and tells you exactly when you must open the door and talk
  to the person next door.
- **The pester test** — count interruptions, not boxes. If every
  task starts with "wait, is anyone touching the order module?",
  the diagram lies and the coupling tells the truth.
- **Conway, run forward** — four people, so design four
  work-streams with thin agreed interfaces. The interfaces are
  where pestering is allowed.
- **Agents too** — modular design is what makes coding agents
  parallelisable. One worktree per agent only works if modules do
  not stomp each other. High coupling = merge conflicts = an
  architecture smell with a token bill.

### 1.2 Eight patterns, and the scar on each

- **Layered** — presentation / business / data access / database.
  Each layer hides its internals behind a stable interface. LAMP
  ran the 2000s web this way; database engines were swappable.
  *Scar:* ossification. Thirteen tiers, and a customer address
  change touches seven.
- **Event-driven** — producers publish, consumers react, nobody
  calls anybody. A broker classifies events and keeps the list of
  who cares about what. *Scar:* debugging. No global ordering.
  Correlation IDs on every event, no exceptions.
- **Microkernel** — a minimal core, everything else a plug-in.
  Eclipse, VS Code. *Scar:* a plug-in jungle once each plug-in
  invents its own API style. A microkernel without governance rots.
- **Microservices** — modularity extended to deployment: small,
  independently deployable, owning its own data. Netflix runs
  hundreds. *Scar:* one loan application, 47 service calls, 10
  teams, nobody able to debug the path. Demands DevOps maturity.
- **Space-based** — computation over replicated shared memory, no
  single database choke point. *Scar:* replica divergence; CRDTs
  fix it and performance falls.
- **Client-server / manager-agent** — clients talk to a server
  owning shared state. One manager delegates to many agents (SNMP;
  also your N1 agent-herding worktrees).
- **Pipe-filter** — data flows through transformers. Compilers,
  Unix pipes, `downcase | tokenise | stem | stopWords | tfIdf |
  cluster`. *Limit:* pipes are a one-way street; poor fit for GUIs
  where users act in any order.
- **The modern web** — LAMP and MEAN gave way to Jamstack,
  serverless, micro-frontends, edge logic. Same trade every
  generation: more scale, more moving parts, harder debugging.

### 1.3 Design essentials

- **Coupling** — how much modules know about each other. Low
  coupling = changes stay local. The 13-tier address change and the
  47-call loan app are both coupling failures, from opposite ends.
- **Cohesion** — how much a module's insides belong together. High
  cohesion = one job, nameable in one sentence. If you need "and"
  to describe a class, it is two classes.
- **Information hiding** (Parnas, 1972) — modules hide *decisions*,
  not just data. Hide what is most likely to change: file format,
  vendor API, pricing rule.
- **Design-for-test** — if a thing is hard to test, redesign the
  thing. Pass dependencies in, keep I/O at the edges, logic in pure
  functions. Your tests are the first customer of your
  architecture.
- **Mock** — a hardcoded stand-in behind a published interface, so
  you can test a thing that is not built yet. Falls straight out of
  Parnas: interfaces first, internals later.

### 1.4 Choosing, for a four-person month

| Situation | Reach for |
|---|---|
| Default. Web/mobile app, one team | Layered monolith, client-server |
| Batch data, ML pipeline | Pipe-filter |
| A tool others should extend | Microkernel |
| Genuinely event-shaped domain | Event-driven, one broker, correlation IDs day one |
| Résumé says "I wanted microservices" | Layered monolith. Split in proj3 if the seams demand it |

**You are four people. You are not Netflix. Build the monolith
first.** A modular monolith you can split later beats a distributed
system you cannot debug now. Boring technology is a feature: every
exciting choice spends innovation budget you need for the product.

### 1.5 1b clinic

- **The budget is arithmetic** — 4 people × 10 hours × 4 weeks =
  **160 person-hours**, and testing takes its share.
- **Safe / bold / wild** — a good proposal is mostly safe, one
  bold, wild only with a kill signal defined ("if the API key does
  not arrive by week 2, we ship the mock"). Four wild milestones is
  a pre-written apology.
- **Name your architecture** — which pattern, why, and the one
  trade-off you are knowingly accepting. One paragraph. It becomes
  your proj2 README design section.

## 2. Beyond the notes

### 2.1 Loose ends from the W3 recap

The think-pair-share turned up material the N3 notes do not carry.

- **The -ility pairs are at war, concretely.** *Security vs
  availability:* secure means nobody can reach you; available means
  customers can. *Portability vs scalability:* you go fast by
  exploiting a local quirk of hardware or data, and that quirk is
  exactly what breaks in the cloud. *Maintainability vs
  reliability:* see xz below.
- **xz / liblzma.** Maintainability was excellent — widely used,
  everyone depended on it. Reliability was catastrophic. No
  password cracking, no buffer overflow: a two-year social
  engineering campaign. Say hello, ask about the kids, sympathise
  about burnout, suggest a co-maintainer, and the attacker inherits
  root on every distro. 75–95% of modern software is reused open
  source, so the **attack surface is everything you wrote plus
  everything you downloaded**.
- **Premature optimisation, and the fix.** The bottleneck is never
  where you guessed; it is in some tiny corner. Write version one
  cleanly, then put a profiler on it. Timm's case: `cProfile`
  found an obscure string-to-date coercion; dropping the type ran
  10× faster.
- **"Test what you fly, fly what you test"** (NASA). The same
  paint, the same wires — not an approximation.
- **The ground system counts.** 40% of deep-space software
  anomalies were *ground* software. One Saturn mission bottlenecked
  on a Microsoft Access database in Ohio: block one end of the
  garden hose and the pressure backs up all the way to orbit.

### 2.2 Layered, worked live: data / model / dialog

The notes give the LAMP tiers. The lecture built the other classic
three-layer stack on the board, and the interesting part was the
seam.

- **Data layer** — storage, fast access, IO. B+ tree or markdown
  files: nobody upstairs cares.
- **Model layer** — business concepts, unpolluted by storage
  detail. **The model holds what is true.**
- **Dialog layer** — **holds what *might* be true.** A half-filled
  insurance policy is a fake. `submit` is the moment the fake
  crosses the line and becomes real.

**Closures as the proxy.** The two layers must talk without knowing
each other. So the model hands the dialog a function: "here is the
OK button; when it is pressed, run this." The dialog has no idea
what it does — updates data, increments income counters,
calculates tax, notifies the inspector who must now visit the new
butcher every three months. The dialog only knows a button exists.
The model bubbles one function above the waterline and keeps the
rest submerged.

Two test questions with the same answer: what does the dialog tell
the model when the user hits **cancel**? Nothing — and note the
closure simply never ran. What does it tell the model when the user
**resizes the window**? Nothing.

**Where does `age = 0..120` live?** Everybody needs it. The data
layer bins it for indexing; the model reasons over it; the dialog
must reject `130` and `abc`. Four answers surfaced in class:

1. *In the dialog.* Fast rejection, but now the rule lives in one
   on-prem window while the model scales on the cloud, and the
   cloud does not know it.
2. *In the model, checked on submit.* Dialog sends values, model
   returns an error. Correct, but a network round trip per
   keystroke-worth of validation.
3. *In the model, published as constraint functions.* When the
   model wakes the dialog it hands over the OK closure **and** a
   bag of little constraint functions, one per editable cell. Each
   takes a value, returns true/false or an error string. The dialog
   knows "a constraint", not "age".
4. *In neither.* A config file, and the build system copies the
   constraint into dialog, model and schema. Ruby on Rails
   (three-layer, Ruby, and very fast to field a web app around
   2003) worked this way.

### 2.3 Deriving the observer from a problem

Two people have Tim open. One is settling his superannuation; the
other edits his address to the cemetery. How does view one learn?

- **Poll.** Ask "is the address current?" every few milliseconds.
  That is your CPU gone, times a hundred thousand users.
- **Push.** The writer tells a **broker**; the broker holds a list
  of who registered interest in Tim; it notifies them. Nothing
  happens until somebody actually changes something.

Note two properties. It is a **star network, not a fully connected
one** — n edges to maintain, not n². And there is **no monitor
burning CPU** looking for change.

That is the same object under three names: **model-view-control**,
**subject-observer**, **event-driven with a broker**. A new agent
joins by tapping the broker: "any thermometer data, send it to me."

**The broker starts smelling like an operating system.** Give
agents priorities, deliver different events to different consumers
at different times, and your simple distributed thing has become a
scheduler. And if the traffic it carries is peaky and bursty, so
are the internal event streams — which is why event systems debug
badly.

Event-driven gives you flexibility, which is great, and too much
flexibility, which is bad: if anybody can call anybody after
anybody, how do you prove anything terminates in reasonable time?
Timm's own line: as a beginner, starting from scratch, he would
reach for it — but he would not use it for the whole world hitting
one public page.

### 2.4 One layer down: SQL, JSON, and why the seam holds

- **SQL is a deliberately minimal proxy language** — the thin,
  uniform pipeline that makes the "swap the database" promise
  sayable. Everything is a table; cells are atoms; no nested
  tables. Select rows, project columns, join.
- **A good relational schema is a maintainability design.** One
  place holds Tim's address. Delete, and what should go, goes.
  *Cost:* you pull the car apart into the nuts table, the doors
  table, the engine table, and reassemble it at runtime.
- **JSON is nested dictionaries: one-to-n, and only one-to-n.**
  Fine when the child dies with the parent — destroy the car,
  destroy the doors. Wrong when it does not: the cupholder you
  resell on eBay, the mechanic who services other cars too.
- **Nesting makes traversal asymmetric.** "What parts does
  OfficeMax supply?" is a lookup. "Who sells coloured pens?" walks
  every supplier and every part. Flat tables make both the same
  computation.
- **The promise held officially, not in practice.** Database quirks
  locked people in. And MEAN answered the layer idea from the other
  side: JavaScript all the way up and down, so a trick learned at
  the Angular layer transfers to Node. Separation of concerns keeps
  your skills from travelling too.
- **When layers get bypassed.** The OSI seven-layer model has an
  industry per layer. Traders paid in microseconds punch straight
  through the stack. And TCP/IP became useful precisely by
  collapsing several OSI layers into one usable thing — a reminder
  that the goalposts move.

### 2.5 Bell Labs and the pipe

The pipe was not an idea, it was an organisational answer.

**The constraint.** Antitrust broke Bell into competing regional
companies sharing one physical wire. Research could not be
centralised without looking like a monopoly again. So they asked
for *distributed, coordinated* development: everything separate,
somehow working together.

**The building.** Bell Labs took a third of the era's new computer
science PhDs. No job descriptions — you succeeded if other people
used your tools. A design rule, not a joke: walking to the toilet
you passed at least twenty open offices. Shannon rode a motorcycle
down the corridor.

**The metaphor.** McIlroy: software should be like a garden hose.
It does something; want something else, screw another filter on the
end.

**What the `|` actually is.** Not a temporary file — that is the
impoverished MS-DOS cousin. The Unix pipe is a **buffer plus
process control**: it minimises file IO, and because each stage
blocks until its input buffer fills, the operating system suddenly
has five processes it can schedule and pause. One symbol bought
concurrency control.

**Separation of concerns, in five characters.** `sort | uniq`:
`uniq` compares line *i* with line *i+1* only, and is therefore
tiny and memory-efficient — *because the sort is upstream*. Why
does `uniq` not sort? Why should it. And `sort` does not care about
duplicates; it just does merge sort, and will happily push ten
megabytes through one megabyte of RAM.

**Where the tools live.** No central approved repository — `PATH`.
Put `$HOME/bin` ahead of `/usr/bin` and your tools win. Tell a
colleague to add your bin, and they have your whole toolkit.
Decentralised, coordinated.

**What they refused.** Y-shapes. Fan-out. Feeding the last stage's
output back round. All buildable, all rejected: they traded
generality for a usability they could keep. The night the pipe was
coded, the next day was "an orgy of recoding" (the official Unix
history's word) — every big program busted into small utilities.

**Still true today.** Timm's own 15-year-old text mining pipeline
ran an awk script into a shell script into a pile of Java, four
languages, no recompilation. And when Claude Code churns, look at
what scrolls past: `cat`, `grep`, `sed`, `sort`. One-off shell
queries, all the way down.

### 2.6 Microkernel hubris

The microkernel temptation is real: work with anything long enough
and you find primitives nobody saw. Timm's own case — after years
teaching optimisation, regression, classification, clustering as
separate things, he found that once you cluster the data,
classification *is* "find the nearest cluster, report the expected
value", and so is regression. Same primitive. He now writes papers
on the microkernel that falls out of it. When he explains it,
people say: those are separate things, what are you talking about?

Then the cautionary tale, which is the entire history of Linux.

- Torvalds designed a **monolithic** kernel, a big box with many
  APIs.
- **Tanenbaum** — who wrote the operating systems textbook and
  Minix, a teaching microkernel — publicly said he would give
  Torvalds an **F**, because microkernels were obviously the
  future.
- **Stallman** — who gave us Emacs and a platform-independent
  optimising C compiler in the 1980s, the workhorse of the entire
  open source world — went the microkernel route too.
- Torvalds shipped, and got an army of contributors, *because the
  chunky kernel was something everyone could understand.* Stallman
  never shipped the kernel. A microkernel means some function
  nobody has heard of is called twelve thousand times a
  microsecond, and every interaction has to be right.

No slouch of a programmer failed at this. **Don't be too clever.**
You get less to code, you think you bought maintainability, and you
may have bought a comprehension nightmare. Timm's advice for your
project: almost certainly not — building a good microkernel is
senior-monk work.

### 2.7 The scissors: how we got to microservices

One story, four cuts, and the cost is visible at the end.

1. **2003, a cloud instance is a machine.** You pay, they boot a
   Unix on real metal. Three or four minutes to come up.
2. **Virtual machines.** Boot the metal once, run many small
   operating systems on top. Now you can pick a 4 GB instance up
   like a grape and drop it on a less busy host. Scheduling
   appears.
3. **Containers.** Someone noticed the namespace table inside
   Linux: chop it, and one virtual OS holds several separate
   namespaces. Pull a card out of the deck and its whole namespace
   comes with it. Inside: file system, editors, debuggers.
4. **Microservices.** Now look at what that card actually does —
   connect a database to a regulator, send JSON, quit, seven
   million times a minute. It never touches the file system or the
   editors. So shred the card and keep only the path you walk. A
   tiny unit of transfer: thousands per node, cheap to move when a
   node gets hot.

**Then the bill.** Why do operating systems have file systems and
editors, if programs just run? Because programs also **crash** —
and a crash wants a log to write to and a stack you can walk with
decent tools. The microservice has no file system to hold the log
and no room for the gadgets that read the stack. You shredded
exactly the debugging apparatus. That is the whole microservices
trade in one sentence: 1.8 GB of a 4 GB VM sits unused and is pure
waste, and the waste was where your error messages lived.

(And the same scissors elsewhere: **space-based** is kids loose in
a backyard, agreeing to pile any ball they find against the fence.
No permissions, no locks, wonderfully fast — and someone takes the
ball you were saving for tomorrow.)

**Client-server, from the other side.** Push work to the client:
the browser now hosts real virtual machines, even Python, so all
dialog CPU and input checking costs the cloud nothing. The centre
keeps what only a centre can do — storage, authorisation,
communication. If you are smart you do as much locally as possible
and minimise network chatter. *The failure mode:* centralise
everything and the cloud going down takes you with it; so you
cache; and now you own cache invalidation.

### 2.8 Coupling and cohesion: two failures and a doorman

**Google's signal firehose.** Even logged out, your laptop
broadcasts; Google knows where you are. So the user-monitoring team
had a vast database, and the machine learning team — being machine
learning people — built models over **every** field in it. The
consequence was not the obvious one (yes, that pipeline is also a
breach waiting to happen). It was that the front end could no
longer change: every interface change broke a model. High coupling
means you cannot change anything.

The fix is a feature selection exercise: find the fields that carry
real signal, drop the rest, and agree the front end guarantees
*those* and only those. Coupling reduced by contract.

**The API rule.** *You only get to design an API once.* Publish it
and somebody builds their entire application on one corner of it.
So publish small interfaces you can still change, never large
complicated ones.

**The doorman.** Cohesion, as a confession: reading rows off disk
gives you strings, so Timm's model code was littered with "is this
column numeric, coerce it" checks. He gave a lecture on cohesion,
looked at his own code, and thought: *what a load of rubbish.* Why
is the model polluted with string parsing? Coercion now happens
once, at load time, in the data layer — the doorman outside the
hotel. The model inside receives ints and floats and never thinks
about disks again.

### 2.9 Parnas, 1972

**Who.** David Parnas, a towering figure, and the man who publicly
quit Reagan's missile shield panel. The design, not a joke: nuclear
reactors idling on the ground, dumping their entire output as a
microwave burst into an orbiting mirror, focused onto a missile
during the few milliseconds it is above the atmosphere. Parnas —
decades on software, decades on missiles, no problem with reactors
— said this is rubbish, and resigned in public.

**What.** *On the criteria to be used in decomposing systems into
modules.* Written when the military was writing software bigger
than anyone had written before, and the standard picture was one
enormous flowchart where everybody could see everything. Parnas
said that will not scale, and invented the module.

**The order is the point.** Every team publishes its interface
first. Then everyone can talk to everyone. Then, and only then, you
work on internals. That is how large teams coordinate — and it is
where mocks come from: the interface exists, the internals do not,
so hardcode a few answers and test today.

**Hiding, in four examples.** Python's nanosecond timer — talking
to hardware clocks somehow, and Timm has no idea and does not care.
Reading a file: blocks, scattered non-contiguously, and a read-ahead
heuristic that grabs the next block because you will probably want
it. McDonald's: a screen, then a window, and a fish burger. Your
own body: the liver is a huge nasty chemical factory because
fat-soluble waste is hard to process at body temperature, the
kidney is small and simple because water-soluble waste is easy, and
you have four or five circulatory systems — and you have been using
the thing for years without knowing.

**Design for test, one red flag.** "…and next month we start
testing." Some system-level work genuinely waits. But five people
sharing code need a test suite they can run on their own laptop
before they push.

### 2.10 Feature toggles: the architecture you actually have

**A/B testing** ships the feature to 1% of users and compares. One
way to implement it: boolean **feature toggles** all over the code,
flipped by a config file.

Peter Rigby (FSE 2017-ish, worth reading generally) went to Google
and asked for the design of a big system. He got a clean tree —
about fifteen nodes, each hundreds of thousands of lines. Then he
mapped the feature flags. They were a **spiderweb stretched across
the whole design**. To do anything, box one had to talk to box two.

Timm's first reading: they got the initial design wrong. His second
reading, which is the one to keep: the tree was a good enough
approximation to get teams moving, and years of real work grew the
real connections. **The toggles are an EEG cap on the system — they
read out the dependencies you actually have, not the ones you drew.**

**The pause.** Timm described this to Linux Foundation people, who
had not heard of A/B testing. They asked: *you mean Google fields
software containing dead code, turned on by a config file?* Yes.
*We do not do that.* When the kernel ships, it means it. You do not
leave a sleeping circus in the corner of the operating system, and
when you test a thing you test the whole thing — fly what you test.

**Why the difference?** Class answers, all partly right: Google
sells services and monetises engagement, so speed of strapping on a
new box wins; the Linux Foundation sells one product and its entire
reputation is that kernel; Google has many teams per module, the
kernel has unusually tight coordination and unusually experienced
people who know what you may not do. Timm's verdict: drop those
same kernel engineers into a distributed cloud shop where they
control nothing, and they would grow a spiderweb too. Architecture
is not only technical.

### 2.11 What actually kills projects

High on the list, in order of how often Timm has watched it happen:

- A bad architectural choice.
- Choosing something **your people do not understand**.
- Choosing something **without vendor support** — and, inversely,
  extensive vendor support is high on the list of what makes
  projects work. Note this cuts against the beautiful choice: in
  LAMP there was a whole industry waiting to help with your MySQL
  layer.

And there is no best architecture. Things that looked like bad
ideas get rescued when someone moves the goalposts (OSI →
TCP/IP). A standard business plan is: invent an architecture, sell
the tooling, convince the world this is how things are done — and a
lot of what we build on came from exactly that.

**Why read architecture books at all**, if you will only ever use
one or two? It is the footballer running laps in the off-season.
The one you use has to be the right one. And seniority shows here:
the more senior you are, the less time you spend bracket-matching
and the more you spend arguing about shapes.

### 2.12 The AI half-hour

Before architecture, an hour on where LLMs actually stand.

**Local vs foundation models (the 1a results).** Local models did
worse, as predicted; Claude read as the all-rounder, the others
each had a compromise somewhere. **The class's objection is the
important part:** people ran local models bare and foundation
models inside harnesses. That is not a fair comparison — the
harness is doing work. Timm's expectation stands anyway, and his
second expectation is that it stops being true in two or three
years.

**No, you cannot download the weights.** Weights are node and edge
values over a *topology*; they mean nothing in a model with a
different shape and different internal dimensions. What *does*
work is exercising a model's input/output behaviour and training on
that — which is how some recent models were reverse-engineered
fast.

**Why the internal space is unreadable** — the kernel trick, on the
board. Red dots ringed by blue dots: no threshold on x or y
separates them (*not linearly separable*), but synthesise a third
dimension from x and y and a flat boundary appears. That was 1998.
An LLM does this at scale: each layer maps into another learned
space. "Tim has a long moustache" is readable at layer zero and
magic at layer one. Timm's students are finding heavy regularity in
those per-layer output vectors — cluster each layer's output, learn
a decision tree from input to target, throw away the middle, and
you have a surrogate. Low intrinsic dimensionality means
compression is possible.

**Red Hat's three-act story.** 2022: management says *you shall use
AI*, nobody knows how, Red Hat makes a lot of money on very
network- and system-intensive work. A year later the token bill
arrives and management says *what*. Now every customer conversation
is about **control, regulation and minimisation** — which means
somebody has to set the policy and somebody has to monitor it.
Timm, deadpan: *people might be needed to understand things.*
Corroboration: internships are back this year after a thin couple
of years, and Red Hat was on campus hiring.

**The man hanging upside down.** He wrote autonomous vehicle
software, so he knew to keep a watching brief on the car. After a
month of flawless driving on shady country roads he relaxed. It
takes about nine seconds to snap from relaxed back to supervisor.
Car accidents take three to five. He woke up inverted with his kids
shaking him. **Nearly-perfect automation is the dangerous kind**,
because it trains you out of watching.

**Timm's own LLM ledger.** The win: 160,000 lines of JavaScript
ported to TypeScript and then Rust by one grad student over a
weekend — three versions on Monday where there was one on Friday.
It worked *because years of hand-building had left an extensive
test suite*. The losses, both on a non-monotonic theorem prover
(one that can un-decide things, and must then un-decide everything
that depended on them):

- For four weeks the model insisted there were nuanced complexities
  in the undo path, with special functions and special names. Timm
  was drafting a paper about them. Variance kept climbing. He threw
  a fit and wrote a frankly emotional prompt — *I don't think
  you're listening to me, this is too complicated, what is going
  on* — and five minutes later got a much simpler design that
  worked. The special cases had never existed. **It made things up
  and defended them staunchly.**
- Evaluating against rival systems, he moved to tasks two through
  five. Under that cognitive load he stopped watching task one. The
  model had been quietly rewriting the finished, relied-upon
  kernel for four or five days before he noticed.

The rule he draws: **team-LLM for requirements engineering, for
feature extraction over piles of text, for going where nobody has
gone** — anywhere control is cheap and the blast radius is small.
Nervous as hell for the semantic kernel of software that matters,
where task two onward now moves slowly with enough tests to detect
task one being disturbed.

**And the reason this course exists.** For years, "build me
software" produced menu systems, library catalogues, calorie
counters. Pointing an LLM at the spec and asking *what is nobody
doing, and what is the least I need to do to get there* is what is
producing this cohort's genuinely odd proposals.

**Why software engineering is easy to model.** Repeated result over
decades of mining projects: astonishingly little data is needed to
decide well. Grass is the product of billions of years of
accumulated accident; software is a deliberate attempt to make
something another human can understand, so **we manufacture
regularity**, and the regularity is minable. The showcase: Google's
test suite once took two weeks to give feedback and people were
resigning over it. Reordering tests so that half the failures show
up in the first hour needed three variables — *has it been tested
before, when did it last crash, is it new.* Not languages, not
expertise, not workload, not platform.

## 3. Review questions

Ten questions, ~7 minutes each. **(a)** recall, **(b)** analysis
or transfer. Each part hands you a piece of the answer; supply the
rest.

**1. What architecture is for**
(a) A good architecture tells you two things. One is *what is
yours* — the part you can change with the door shut. Name the
other thing it tells you, and state the pester test in one
sentence.
(b) Four people, four work-streams. Example of the failure: if the
UI and the data model end up in one stream, its owner becomes
everybody's bottleneck. Name your 1b work-streams, then name the
**two** interfaces that will be crossed most often and say which
one you expect to argue about.

**2. Layers and their seam**
(a) In the data/model/dialog stack, the **dialog** layer holds what
*might* be true — a half-typed insurance policy is a fake. Say what
the **model** layer holds, and say what `submit` does to a fake.
(b) The rule "age is 0..120" could live in the dialog, in the
model, in the data layer, or in a config file the build copies into
all three. Example of a break: put it only in the dialog, move the
model to the cloud, and the cloud now enforces nothing. Pick the
place you would use when the model runs on the cloud and the dialog
runs on prem, and give **two** more breakages, one per rejected
option.

**3. Handing over a function**
The model does not want the dialog to know any business rules. So
it hands the dialog a **function** and says: when the OK button is
pressed, call this. The dialog stores it, calls it on OK, and never
looks inside. (That wrapped-up function is called a *closure*;
you meet them properly in week 6.)
(a) The function might update the database, recalculate tax, and
notify a health inspector. List what the **dialog** has to know
about any of that.
(b) The user hits cancel, then resizes the window. On cancel the
dialog tells the model nothing — and note the function simply never
ran. Say what the dialog tells the model on **resize**, and then
say what would have to be true of the dialog's code for the answer
to be "something".

**4. Keeping two views in sync**
Two staff have Tim's record open. One changes his address. The
other must see it.
(a) One design is to poll: every few milliseconds, ask "is this
still current?" Give the other design (the one using a broker), and
state the CPU objection to polling.
(b) The broker "starts smelling like an operating system" once it
does more than route. One example: giving agents priorities. Give
**two** more things you could add to a broker that push it further
towards being a scheduler.

**5. The scissors**
(a) The cuts run: real machine (2003) → virtual machine →
container → microservice. The container cut worked by slicing the
Linux namespace table so one virtual OS holds several separate
namespaces. Say what the **microservice** cut removes from a
container, and why that makes it cheap to move between nodes.
(b) The thing the last cut threw away was the file system and the
stack-inspection tools — i.e. where a crash writes its log. Given
that: name **one** kind of project that should still use
microservices, and say what that project must already own before
the trade is safe.

**6. Pipe-filter**
(a) `sort | uniq`: because `sort` runs upstream, `uniq` only ever
compares line *i* with line *i+1*, so it stays tiny and
memory-efficient. Say why `uniq` was **not** given a built-in sort,
using the term from §1.3 that names the principle.
(b) Unix pipes are a one-way street; Bell Labs deliberately
refused Y-shapes and feedback loops. Example of the payoff: any
stage can be written in any language, and the operating system can
schedule five of them without knowing what they do. Name **one**
task in your 1b product that a straight pipeline could not express,
and say what you would use there instead.

**7. Microkernel hubris**
(a) Tanenbaum said he would give Torvalds an **F**, because
microkernels were obviously the future. Say what Torvalds had built
instead, and say who shipped a working kernel.
(b) Stallman was no slouch — he wrote Emacs and a
platform-independent optimising C compiler — and still never
shipped the microkernel. One reason: in a microkernel, some
function nobody has heard of gets called twelve thousand times a
microsecond, and every interaction must be right. Give **one**
other reason a chunky design can beat an elegant one, thinking
about who else has to work on it.

**8. Coupling, cohesion, hiding**
(a) The API rule is: *you only get to design an API once*, because
someone will build their whole product on one corner of it. State
the practical instruction that follows for the size of interfaces
you publish.
(b) Google's ML models consumed every user signal, so the front end
could no longer change without breaking a model — high coupling
means you cannot change anything. The fix was feature selection
plus a contract guaranteeing only the chosen fields. Name the
equivalent in your project: one thing you cannot now change because
something downstream eats all of it, and write the one-sentence
contract that frees it.

**9. Feature toggles**
(a) A feature toggle is a boolean flag, set from a config file,
that switches a feature on for some users and off for others —
which is how you run an A/B test. Say what Rigby found when he drew
Google's toggles onto Google's own clean design diagram.
(b) The Linux Foundation's objection: shipping a kernel containing
dead code that a config file can wake up. One argument for Google's
side: they sell services, and speed of strapping on a new box is
the business. Give **one** argument for the Linux side, then say
which position your 1b product should take and why.

**10. What kills projects**
(a) Three architecture-related project killers were listed. One is
choosing something **your people do not understand**. Name the
other two.
(b) "Build the monolith first" and "pick the pattern that fits the
domain" can disagree. Example: an alerts-and-streams product is
genuinely event-shaped, yet four students with no broker experience
will drown in it. State which way you resolve it for your own 1b
architecture paragraph, and name the trade-off you are knowingly
accepting.

## 4. Answers, briefly

Part (b) is often about *your* product, so there is no single right
answer. What is marked is the shape: a named concrete thing, a
named consequence, and a commitment.

**A1.** (a) It also tells you *when you must talk to someone else*
— where your part stops and the negotiation starts. Pester test:
count interruptions, not boxes; if most tasks open with "is anyone
touching the order module?", the coupling is real whatever the
diagram says. (b) Shape: four streams that can each run a day
without permission, and two interfaces named as data, not as
vibes. Worked example — streams = ingest, matching/pricing, API +
web, eval harness; the crossed interfaces are (1) the order record
schema, (2) the pricing call signature. Expect the argument at the
order record, because every stream wants one more field in it.

**A2.** (a) The model holds **what is true**. `submit` is the
moment the fake crosses the line and becomes real — the dialog's
tentative object is committed to the model, which then does the
real-world work (store, recalc, notify). (b) Best answer for
cloud-model/on-prem-dialog: the model **publishes the constraint
as a function** the dialog can call locally, or a config file the
build copies into all three layers. Two more breakages: put it only
in the **model** and every keystroke's validation needs a network
round trip; put it only in the **data layer** and the dialog
cannot reject 130 until after a failed write, so the user learns
about it last. (Fourth option, the config file, fails differently:
nothing enforces that the three copies were rebuilt together.)

**A3.** (a) Nothing. The dialog knows one fact: a button exists and
something must be called when it is pressed. Not what the function
touches, not that a database or a tax rule or an inspector exists.
(b) On resize: nothing. The only way the answer becomes "something"
is if the dialog's code contains knowledge that belongs to the
model — e.g. it recomputes a layout from business rules, or caches
model state it must now invalidate. That is the test: any event
that forces dialog→model chatter marks a rule stored on the wrong
side.

**A4.** (a) Broker design: the writer notifies a broker; the broker
holds a registry of who asked about Tim; it pushes the change to
those watchers only. Nothing happens until someone actually writes.
CPU objection: polling burns cycles asking a question whose answer
is almost always "no", and the cost is per-view per-interval — at a
hundred thousand users it is the whole machine. (Bonus: star
network, n edges, not n².) (b) Two more: **queueing/buffering**
(events held when a consumer is slow) and **filtering or routing
rules per consumer**. Also acceptable: retry and delivery
guarantees; ordering; dead-letter handling; access control on who
may subscribe to what. Each one is a scheduler feature.

**A5.** (a) The microservice cut removes everything the running
task never touches — file system, editors, debuggers, most of the
OS — keeping only the path actually walked. Cheap to move because
the unit of transfer is now tiny, so thousands fit on a node and
rebalancing a hot node is fast. (b) One good answer: a
high-volume, well-understood, stateless transform (image resize,
request auth, event forwarding) at an organisation that runs it
millions of times a day. What it must already own: centralised
observability — log aggregation, distributed tracing, correlation
IDs — because the crash has nowhere local to write.

**A6.** (a) **Separation of concerns** (equally: cohesion — `uniq`
has one job, nameable in one sentence). `sort` does not care about
duplicates, `uniq` does not care about ordering, and the pipeline
composes them. Putting a sort inside `uniq` would duplicate a tool
that already exists and make both harder to reuse. (b) Anything
interactive or order-free: a UI where the user can act in any
sequence, an editing session with undo, a request that must go out
and come back. Use client-server or an event/observer design
there; keep the pipeline for the batch and ML paths.

**A7.** (a) Torvalds built a **monolithic** kernel — one big box
with many APIs. **Torvalds** shipped. (b) Any of: a chunky design
is **understandable**, so volunteers can read it, debug it and
contribute — a monolith recruits an army, an elegant microkernel
recruits nobody; fewer interactions to get right, so it can be
wrong in one place and still boot; you can ship it unfinished and
improve it in public, whereas the microkernel is only correct when
*all* the interactions are correct. General form: shipping beats
elegance when the missing resource is other people's attention.

**A8.** (a) Publish **small** interfaces you can still change;
never large complicated ones. (You do not get a second draft, so
minimise what you are committing to.) (b) Shape: name one
downstream consumer, name the thing it eats *in full*, name the
narrowed contract. Worked example — "our React front end reads the
whole order row, so any column rename breaks it. Contract: the
front end may depend on `{id, status, eta, total}` only; everything
else is internal and may change without notice." Marks for a
contract that is checkable, not a promise to be careful.

**A9.** (a) The toggles did not sit inside the boxes. They formed a
**spiderweb stretched across the whole design** — to do anything,
box one had to talk to box two. Reading to keep: the clean tree was
a fine approximation for starting the teams, and years of real work
grew the real dependencies; the toggles read out the architecture
you *have*, like an EEG cap, not the one you drew. (b) For Linux:
you ship what you tested — dead code in the kernel means the
fielded artefact is not the tested artefact (fly what you test);
dormant code is attack surface and maintenance burden nobody
exercises; a flag matrix multiplies configurations faster than you
can test them. For 1b: with four people and one month, take the
Linux position — you cannot test 2^n configurations. One toggle
for one genuinely risky milestone (the kill-signal switch) is
defensible; a toggle habit is not.

**A10.** (a) A bad architectural choice; choosing something with
**no vendor/community support**. (Succeeds more often: extensive
vendor support.) (b) Shape: pick a side, name the cost you accept,
and name the signal that would change your mind. Worked example —
"Our alerts domain is event-shaped, but nobody here has run a
broker, so: layered monolith with an internal event bus (one
module, in-process). Trade-off accepted: we cannot scale consumers
independently. If week-3 load testing shows the notifier blocking
the API, we move that one module behind a real broker in proj3."
