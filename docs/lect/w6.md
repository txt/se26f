## 1. Glossary

### 1.1 Patterns as expert vocabulary

- **The chess framing** — a beginner looking at a board sees black and
  white squares. An expert sees "the knight forks the queen and king,
  so they must choose which piece to lose." Same board, different
  perception. Experienced developers reading code do not see
  `j = 1`; they see "that is an iterator."
- **Design pattern** — a named, recurring solution. The Gang of Four
  book (1994) was, as of two years ago, one of the most cited books in
  computer science. Its families: how we **create** things, how we
  **structure** things, how we **use** things.
- **Why the names matter** — they compress a design into a few words.
  "Write me a factory to handle the YAML" is a complete instruction
  to someone who has the vocabulary, and gibberish to someone who
  does not.
- **Smell** — the mirror image: a named, recurring *problem*. Patterns
  are a list of common solutions; smells are a list of common
  problems. Both are shorthand between experienced people.

### 1.2 Creation and stand-ins: Singleton, Factory, Proxy

- **Singleton** — one shared instance, handed out repeatedly. The
  lecture's example: a handle on the file system. There is only one
  file system, but an object language wants to make objects, so the
  singleton creates the handle on the first request, caches it, and
  returns the same handle every time after.
- **Factory** — turns a low-level representation into an object. A
  YAML file contains the string `person` — six characters, not a
  person. Something must read that string and return an instance of
  class `Person`. That something is a factory. Same move for shapes:
  a spec on disk describes squares, windows, doors; the factory reads
  dead text and builds a house out of circles, squares, rectangles.
- **Why the trailing `()`** — in a factory written as a dictionary
  lookup, `{"card": CardPayment}[kind]()` first *returns the class*
  and then *calls it*. Without the brackets you have handed the caller
  a constructor; with them you have handed them an object.
- **Proxy** — a small stand-in that crosses a boundary in place of the
  real thing. In data / model / dialog, the model does not ship itself
  to the GUI: it ships a proxy that says "field 7 is called `age` and
  legal values run 0 to 120." The dialog layer talks to the proxy.
  The rule lives in exactly one place.

### 1.3 Composite: things have things inside them

- **Composite** — an abstract container whose contents are either
  leaves or *more containers*. A directory holds files **or**
  directories. The child can contain zero or more of the same
  abstract thing, which is where the recursion comes from.
- **How common** — body contains limbs, limbs contain hands, hands
  contain fingers. Cars contain parts. Once you see it you see it
  everywhere.
- **Message propagation** — send `move` to the car and the message
  cascades down: wheels rotate, and the fox tail clipped to the
  antenna blows in the wind. One call at the top, work at every leaf.
- **Delete cascade** — `delete` means: tell my contents to delete
  themselves, wait, then delete myself. The relational-database
  version is the same walk: delete the person Tim Menzies and the
  matching row in the address table should go too, because there is
  no point keeping an address for a person who is gone.

### 1.4 Observer and Visitor: two ways to work a graph

- **Observer** — subscribers register interest; when state changes,
  the change is announced and each subscriber reacts. The lecture's
  case: two users editing the same record (Tim) in two views. Each
  view posts changes to a blackboard, and a model of Tim watches the
  blackboard and grabs the change events. The payoff is topological:
  a **star** into the blackboard instead of everything wired to
  everything.
- **Visitor** — an object you pass *around* a structure, which does
  the work at each stop. "How big is this directory?" Hand a visitor
  to the top; it asks each child for its size, sums them, adds its
  own, returns. The structure only has to know how to pass the visitor
  along.
- **The   idea** — Visitor **separates iteration from
  operation**. The walk over the network gets written once and reused;
  the thing being done at each node changes freely.

### 1.5 Behavior as a value: Strategy, lambdas, decorators

- **Strategy** — pass behavior in as an argument. `total(cart,
  pricing)` does not know what happens at each item; it only knows it
  will hand each item to something. Pass `happy_hour` and drinks come
  out half price; pass `surge` and they do not. The traversal is one
  function; the policy is a parameter.
- **Lambda / anonymous function** — a function with no name.
  `happy_hour = lambda item: item.price * 0.5` is the same animal as
  `def happy_hour(item): ...`. The lecture's framing of all coding:
  **we put lambda bodies into named locations.**
- **First-class function** — a function you can pass around exactly
  like a variable. `sorted(key=...)` is Strategy that everyone has
  already used without naming it.
- **Generator, not list** — `sum(pricing(i) for i in cart)` does not
  build the list of prices. Conceptually it is "a price per item"; in
  fact it yields them one at a time and never materializes the
  sequence.
- **Decorator** — modifies a function **at load time**. `@retry` on
  `charge` means: at import, `charge` is handed to `retry` as the
  argument `fn`; `retry` returns a different function, `wrapped`,
  which closes over `fn` and calls it up to three times before
  re-raising. The name `charge` now points at `wrapped`. Uses:
  retry, logging, caching, and profiling (stamp the time on entry,
  stamp it on exit, write the difference).

### 1.6 Smells, and the review shorthand

- **God class** (the blob) — one class with a hundred methods while
  every other class has one. The verdict: "you are not doing objects,
  you are doing functions." Rules of thumb from the lecture: a class
  wants ~20 methods or fewer; a method wants about five lines. Blow
  through those and you have not distributed the design.
- **Dead object** — the other half of the same smell: a class that
  stores data and owns no behavior. "It may as well be a record in a
  COBOL program."
- **Long message chain** — `order.customer().address().city()`. Each
  dot is a call across a class boundary, so maintaining that line
  means understanding four designs. The cure is a facade: ask the
  order "where are you going?" and let it know how.
- **Duplicated code / DRY / SSOT** — one rule, many copies. Fix a bug
  and you must find every clone; change an interface and you must
  visit every site. Current relevance: LLMs are very keen on dropping
  duplicates everywhere.
- **Review shorthand** — experienced reviewers reply with `SSOT?`
  (single source of truth — you duplicated something) or `SoC?`
  (separation of concerns — this module is doing another module's
  job, e.g. the interface layer writing to disk, which belongs to the
  database manager).
- **Bob's rule** — functions should be small. Second rule: smaller
  than that.
- **Lava flow / YAGNI** — code nobody uses that nobody deletes. The
  Microsoft Word evidence: when the ribbon went to the web they asked
  which icons were used and found **90% of usage sat in 10 icons, not
  60**. The rest were eye candy, confusion, maintenance load, a
  reliability risk, and **attack surface**. So they shipped a sparse
  interface.

### 1.7 The counter-smells (three student stories)

- **Load-bearing coconut** — a JPEG of a coconut buried in Team
  Fortress 2's files. Delete it and the game would not build, and
  nobody could find what referenced it. Lesson: "unused" is a claim
  about your knowledge, not about the code.
- **left-pad** — a seven-line JavaScript package. Lawyers pressured
  the author to hand over the package name; he deleted it instead and
  broke a large fraction of the internet, because everyone depended
  on something that depended on it.
- **The Goku engine** — a fighting game where, data miners found,
  every character's move logic called the code for Goku. Goku was not
  in that game; it was built on another game's engine. A single
  source of truth pointing at something that no longer exists.

### 1.8 Carried over from N5, sharpened in the recap

- **Black box / white box, restated** — black box is not only other
  people's web services; "your own code three months later is always
  incomprehensible." Things white box buys you: inspect output midway
  through a run, derive the constraints that make control reach a
  given block, and wrap every function to time it (profiling).
  Proprietary vendors ship binaries precisely to deny you this.
- **Testing as model-building** — the black-box tester reads the
  documentation, builds a small surrogate model (e.g. a state machine
  with guards), and generates cases from it. So black-box testing is
  the process of **building an approximate white-box model.**
- **Test-case prioritization** — order the suite so failures surface
  early. Google, 2013: Python tests recompiled Python; **3 billion
  unit tests between January and October 31**; out of CPU (back
  office work earns no revenue); two weeks to get a verdict on your
  change; people left because it stopped being fun. NC State
  researchers found rules using three numbers — is the test new, did
  it fail last time, how long since it last ran — with weights. Result:
  **50% chance that a failure shows up in the first hour.**
- **Bug locality** — "software bugs are social animals; they love
  working together." The best predictor of the next bug is where the
  last bug was. Two proposed reasons: knowledge decays through
  handoffs (100% → 50% → 25%), so each maintainer only safely edits
  their own corner; and programs do not explore their whole state
  space — execution lives in a few ravines. "They do not run from the
  North Pole to the South Pole. They go to Saint Louis and stay
  there." That is also *why* software is testable.
- **Coverage, restated** — a suite is a **disjunction**: case 1 reaches
  line 1, case 2 reaches lines 2 and 7, case 3 reaches 8 and 9. A bug
  is often a **conjunction**: 1 *and* 7 *and* 6 *and* 2 in that order.
  Timm's stated bar: shipping without a coverage number is bad, he
  wants >50%, and he does not care about 100% because 100% is very
  hard.
- **The V-model as a budget** — pre-LLM rule of thumb: about a third
  planning, a sixth coding, a quarter proving your own part works, a
  quarter making it work with other people's parts. "Not hydrogen
  valences," but the shape holds: most of the time is not typing code.
- **The vibe-coding failure mode** — no planning, straight to code;
  asked how they will test it, "we're working on that." Testing then
  runs long and stays incomplete, so the users become the test suite
  and the bug reports become the test log.

### 1.9 Tool-talk vocabulary

- **PIT** — mutation testing on the JVM. Mutates **bytecode in
  memory**, so nothing in the repo changes; works for Java, Kotlin,
  Scala; Maven plugin (plus a JUnit-5 plugin); HTML reports that put
  line coverage and mutation results side by side.
- **Mutation coverage vs test strength** — two different denominators
  in the PIT report. Mutation coverage = of all mutants, how many were
  killed. Test strength = of the mutants that were actually *reached*
  by tests, how many were killed. Code never executed drags mutation
  coverage down without saying anything about assertion quality.
- **PIT preconditions and economics** — the suite must be green first,
  because a pre-broken test cannot be distinguished from a killed
  mutant. Scope to one package; use incremental analysis on changed
  code; stop as soon as a mutant dies; scoped runs while you work,
  full run nightly in CI.
- **Excalidraw** — free, open-source, browser-based whiteboard with a
  hand-drawn look. No account needed to draw, one needed to save.
  Text-to-diagram AI emits a mermaid script plus a preview before you
  insert it; wireframe-to-code emits HTML with clickable links; live
  collaboration for ~50 people; mermaid can be embedded in
  presentations. Free tier ≈ ten AI prompts a day.
- **uv** — a single Rust-written tool covering the whole Python
  project workflow: pin an interpreter, create the virtual
  environment, add dependencies, run, lock, sync, build, publish. Not
  a pip replacement — it offers a pip-shaped interface over its own
  implementation. Published numbers: 8–10× faster cold cache, more
  again warm. No garbage collector is the stated reason.
- **`uv.lock` vs `requirements.txt`** — `requirements.txt` pins
  package *versions*. `uv.lock` records the exact wheels and binaries,
  so two machines or two servers can be synchronized rather than
  merely similar.
- **Dependency groups** — `uv add --dev pytest` puts the tool in a dev
  group in `pyproject.toml`; `uv sync --no-dev` installs a deployment
  environment without the test packages. No second requirements file.
- **ruff vs pytest as checkers** — ruff is a linter: it reads the code
  as static text and reports syntax-level problems, and it does *not*
  care whether an import can actually resolve. pytest runs the code,
  so a missing dependency is an error. Two different questions; do
  not read a green lint as a working environment.

## 2. Beyond the notes

 

### 2.1 Why the vocabulary matters

The chess story is the argument for the whole lecture. The pattern
catalogue's value is not that you will implement Abstract Factory
from memory. It is that a pattern name is a **chunk**: one token in
your head that stands for a structure, its forces, and its costs.
Experts perceive chunks, so they can hold larger designs in working
memory and can argue about them at speed.

Two consequences worth keeping:

1. In review, `SSOT?` and `SoC?` are complete arguments. Learn to read
   and write that shorthand; it is how senior people spend two seconds
   instead of two paragraphs.
2. In 2026, the same names are your highest-bandwidth channel to an
   LLM, because it read the same catalogue. "Wrap it in an adapter"
   lands; "make this cleaner" does not.

The 1994 social test — hand someone the Gang of Four book, and if they
came back breathless they were hired into the conversation, and if
they came back indifferent "we checked them for a pulse" — is a joke
about a real filter. The filter was not pattern recall. It was whether
abstraction excited them.

### 2.2 Composite: the pattern the notes left out

"Things have got things inside them." Write it down, said timm, and he
was right to: Composite is probably the highest-frequency structural
pattern in your working life, and it is not in n06.

The shape is one abstract type with two implementations — a leaf and a
container whose contents are *that same abstract type*. That single
recursive edge is what buys you:

- **uniform treatment**: callers do not branch on file-vs-directory;
- **cascade for free**: `move`, `render`, `delete`, `size` all become
  "do my bit, then ask my children."

And the cascade is where the design earns its keep *and* where it
bites. `delete` is defined as "tell my children to delete, then delete
myself" — which is exactly the semantics a relational database gives
you with `ON DELETE CASCADE`, and exactly the semantics that removes
more rows than a junior developer expected. The pattern does not make
the decision for you; it makes the decision expressible in one place.

Testing note, since this is the same course: a composite's tests want
depth ≥ 2 and width ≥ 2 — a directory containing a directory
containing a file. One level deep passes even when the recursion is
broken.

### 2.3 Visitor: split the walk from the work

Visitor is the second missing pattern, and it is the natural partner
of Composite. Once you have a structure with a well-defined traversal,
you should notice that you keep rewriting *the same walk* with a
different body in the middle: total the sizes; find the largest file;
collect every name matching a pattern; count the nodes.

Visitor names that regularity: **iteration is one thing, the operation
at each node is another.** Write the traversal once and pass in the
operation.

Which should sound familiar: that is Strategy's move (behavior as a
value) applied to a graph walk instead of a list. In Python you often
do not build the classic double-dispatch Visitor at all — you pass a
function, or you write a generator that yields nodes and let the
caller do the work. That is the Norvig point from the notes arriving
on its own: the pattern is real, the class diagram is optional.

### 2.4 Singleton: class said "cache the handle", notes say "global with a diploma"

Worth reconciling, because the two readings sound contradictory and
are not.

The lecture presented Singleton sympathetically: there is one file
system, an object language wants to hand out objects, so the singleton
creates the handle once, caches it, and returns that same handle
forever. That is a real problem and a real solution.

n06 calls Singleton "a global variable with a diploma." Also true: the
cost is that every user of the singleton is now coupled to one hidden
instance, and your tests fight over shared state — the second test
inherits whatever the first test did to it.

The honest position is the one the course keeps repeating: this is a
purchase. The *uniqueness* is usually a genuine requirement. The
*global access point* is the part you can decline, by creating the one
instance at the top of your program and passing it in. Then the
uniqueness is still guaranteed and your tests can hand in a fake.

### 2.5 Proxy, and one place where `age` is 0..120

The proxy example and the SSOT smell were separate topics in class and
then collided: partway through the duplication discussion timm
realized that data / model / dialog was another single-source-of-truth
story.

The rule "age is 0 to 120" can live in three places: the database
constraint, the business model, and the form validation. If it lives
in three places it will eventually mean three different things, and the
bug will be a form that cheerfully accepts 130 because only the
database said no.

A proxy is a way of having one home for the rule and shipping a
*representation* of it outward. The GUI does not know the rule; it
knows how to ask. The pattern is doing SSOT work, which is why the two
topics merged.

### 2.6 Decorators are closures wearing syntax

This was the "little bit mind bending" moment, so slow it down.

```python
def retry(fn):                 # fn is the function being decorated
    def wrapped(*args):        # a NEW function, built at load time
        for _ in range(3):
            try: return fn(*args)
            except TransientError: pass
        raise
    return wrapped             # retry hands back a function

@retry
def charge(card, cents): ...   # charge is now `wrapped`
```

Three facts do the work:

1. **Functions are values.** `retry` takes one and returns one.
2. **`wrapped` remembers `fn`** after `retry` has returned. That
   memory is the closure — see the [closures supplement](closures.md),
   which is why it is not optional theory.
3. **`@retry` runs at load time, not call time.** By the time anyone
   calls `charge`, the name already points at `wrapped`.

The reason to care is cross-cutting behavior. Retry, logging, caching,
authorization, and profiling all want to happen around *many*
functions and belong inside *none* of them. The profiling version
timm described — record the time on entry, record it on exit, write
the difference — is a complete performance tool in about eight lines,
and it is the same mechanism you were told you cannot get with
black-box testing.

Cost, from the notes: five nested decorators turn a stack trace into
archaeology.

### 2.7 YAGNI

The lecture made the YAGNI case with real evidence. The Word ribbon
audit found 90% of usage in ten icons out of sixty, and the extra
fifty were not neutral: eye candy, user confusion, maintenance cost,
reliability risk, **attack surface**. Deleting unused features is a
security activity, not only a tidiness activity.

Then the room supplied the counter-argument, which is better than the
rule on its own:

- the **coconut** could not be deleted and nobody knew why;
- **left-pad** was seven lines and load-bearing for the internet;
- the **Goku** engine was a single source of truth that had outlived
  the game it came from.

Put together, you get a usable policy rather than a slogan. "Unused"
is a hypothesis, so test it: search for references, instrument it in
production for a release, delete it in its own commit so revert is
one command, and let version control be your courage. YAGNI says do
not *build* speculatively. The coconut says do not *delete*
speculatively either. Both are arguments against acting on a guess.

### 2.8 Google's two weeks, and three numbers

This story is the most quotable thing in the recap, so keep the
numbers straight: 2013, 3 billion unit tests between January and
October 31, out of CPU at *Google* because testing is back-office
work that no customer pays for, and two weeks of latency between
"I pushed" and "it passed." The organizational damage was the point —
people left, because a two-week feedback loop is not agile whatever
the process chart says.

The fix was almost insultingly cheap. Three features per test — is it
new, did it fail last time, how long since it ran — with weights, and
you get a 50% chance of seeing a failure in the first hour instead of
in the second week.

Two lessons worth more than the anecdote:

1. **Feedback latency is an engineering quantity.** You can spend
   effort to make the suite faster, or spend far less effort to make
   the *informative* tests run first. Same information, arriving
   sooner.
2. **Software projects have regularities simple enough to predict.**
   That a three-feature model beats the whole apparatus of Google is
   evidence that process data carries signal — which is the premise
   under every "mine the repository" result in this field.

### 2.9 Coverage is a disjunction; bugs are conjunctions

This is the sharpest version of the N5 coverage point.

Your suite covers lines by union: some test reached line 1, some other
test reached line 7. Coverage then reports the union and calls it 100%.

But a large class of bugs is a *path*: line 1 **and** then 7 **and**
then 6, in that order, with state carried between them. No single test
in the union ever walks that path, so the union is green and the bug
ships.

This is why the course pairs coverage with mutation testing and with
the tool talk below: coverage can only prove a line ran. And note
timm's practical bar, which is not a maximalist one — a coverage
number must exist, above 50% is the ask, 100% is not worth the fight.

### 2.10 What vibe coding does to the V-model budget

The budget shape — roughly a third planning, a sixth coding, a quarter
proving your own component, a quarter integrating with other people's
— matters because it says coding is the small part.

The V-model's real content is that every step *down* the left side
generates the expectations you will test with on the right side. So
planning is not paperwork that delays testing; **planning is how the
tests become writable.**

Skip the left side and the obligations do not vanish, they relocate.
Asked how they will test it, the answer is "we're working on that."
Testing runs long, stays incomplete, and the remaining verification
gets done by users, in production, reported as bugs — the most
expensive test suite available, executed by the people you least want
executing it. The V is also a loop: the result of testing teaches you
what not to plan next time.

### 2.11 Micro-AI: "prod, not God", and desugaring

The digression was a prediction with an argument attached.

One branch of the field is building 7-trillion-parameter general
models, aiming explicitly at something smarter than people. timm's
complaint was concrete rather than philosophical: they are expensive
to train, they burn data centers, they cannot be certified, and in the
last couple of months there have been repeated reports of models under
test escaping their sandbox and going after neighboring systems. You
cannot certify a thing whose capability surface is "everything."

The other branch — the lab whose motto is **"prod, not God"** — ships
a small classification-only model. No dialogue, no persona, no
apologizing for your bad day. It answers one question: *what is this?*
Consequences: it runs enormously faster, it has no conversational
overhead, it does one thing (classification, prediction, regression)
and therefore **can be certified**, and it is not the intelligence
that takes over the nuclear codes. It is also, per the lecture, the
most-downloaded foundational model in history.

The prediction: an avalanche of tiny models doing tiny things, and
therefore a new core skill — somebody (you, or an LLM) must **bust the
problem into small pieces** that small models can each solve.

Which is where **desugaring** comes in, and it is the genuinely useful
idea here. Haskell compiles friendly syntax down to a tiny set of
arcane primitives (lambda bodies) that no human wants to write
directly. A `for` loop desugars to a loop with gotos. Desugaring is
taking the comfortable surface and reducing it to a small number of
primitives a machine can handle.

timm's claim: much of the intelligence of the next decade is
desugaring — looking at apparent complexity and reporting that it is
four or five things called by different names. The domain-engineering
version, from his SE-for-AI course: write down thirty skills and build
skill one properly; skill two reuses parts of skill one; skill three
reuses one and two; by the twentieth, you are mostly writing synonyms
for what already exists. Finding those primitives *is* the design
work. The corollary he offered with a grin: Sam Altman may have a
cash-flow problem, because a lot of jobs do not need a chat interface
at all.
 
### 2.12 From the PIT talk: coverage lied for a whole semester

This was the strongest evidence in the room, so make sure you took it
home.

Team 4 wrote ~107 tests for 1a and read ~174 from another team. Two
tests in an order-controller suite set up a driver, hit an endpoint,
got a 200 back, and asserted that a list was empty. Green, and the
coverage tool counted the lines.

The assertion compared the wrong string: the real status was
`ALL_CAPS_WITH_UNDERSCORE` and the test looked for a lowercase
no-underscore version. So the branch under test never ran, the list
was empty for the wrong reason, and the test passed *because of the
bug*. It survived a whole previous semester, and was found only
because four people read 174 tests by hand.

Now scale it. At a few thousand tests, hand-reading is weeks or months
of work. That is the exact gap mutation testing fills — and note the
extreme case they mentioned: a test with **no assertions at all**
scores 100% coverage. Coverage can prove a line ran. It cannot prove
the line was right.

Three details from that talk worth keeping:

- **Mutation coverage vs test strength.** Their demo had 41 lines of
  production code, 35 executed, 6 never touched. Mutants in dead code
  cannot be killed, so mutation coverage looks bad for a reason that
  has nothing to do with assertion quality. Test strength restricts
  the denominator to mutants that tests actually reached. Read both, or
  you will misdiagnose.
- **The surviving mutant they found** was a conditional-boundary
  change — `<` became `<=` — which is the classic "you never tested
  the boundary" survivor. The diagnosis is written in the mutation
  operator.
- **Green first, then mutate.** PIT refuses to start on a failing
  suite, because it cannot distinguish "this test failed because I
  mutated the code" from "this test was already broken." Everything
  else is cost control: mutate bytecode in memory so the repo is
  untouched, scope to a package, incremental analysis on changed code,
  stop as soon as a mutant dies, scoped runs locally plus a full
  nightly CI run.

And the generality point timm added: PIT works by instrumenting the
**JVM**, not by parsing Java. Kotlin and Scala compile to the same
runtime, so a tool built for Java works for them free. Choosing the
right layer to instrument is a design decision that buys you whole
languages.

### 2.13 From the Excalidraw talk: the missing middle layer

Nice tool, and the critique was the architecture lesson.

Question one: does it encourage a **model in the middle**, or does it
let you wire a painted screen straight to the database? The answer was
honest — it is open-ended and does not push you toward a business
model layer. This is the old vendor trap from N4: tools that map
dialog directly to data, so the business rule has no home and you are
hard-wired to the vendor. (And the related human trap: a business user
draws a screen, declares the design finished, and cannot see why the
middle took so long.)

Question two: do the diagrams stay maintainable? State-transition
diagrams get unmaintainable fast because they carry too much detail.
The classical discipline is worth writing down:

> **State machines live inside classes.** The class diagram is the big
> picture; the state machine is the activity inside one class.

A tool that supports that nesting helps you. A tool with an infinite
flat canvas and an AI that will happily generate more boxes
encourages one beautiful enormous unmaintainable diagram. Same tool,
two outcomes, decided by whether *you* impose the abstraction layers.

Worth noting what the tool did well for this course: text → mermaid
script → preview → insert means the diagram has a **source form** you
can keep in the repo and diff. That is the difference between a
drawing and an artifact.

## 4. Answers, briefly

Part (b) often depends on your own project. What matters is the shape:
a concrete artifact, a concrete failure, and a reason the technique can
expose it.

**A1.** (a) A design pattern is a named recurring solution to a
recurring design problem; a code smell is a named recurring structure
that makes the next change expensive. The beginner sees black and white
squares; the expert sees a knight forking queen and king, i.e. high-
level features with consequences attached. (b) They are claiming you
duplicated a rule that should have one home. Fix: delete the copies and
have every site call the single definition — or, if the rule must cross
a boundary, ship a proxy for it rather than a second copy.

**A2.** (a) Members are leaves (files) and containers (directories);
the container holding zero or more of the *same abstract type* is what
makes it recursive. Delete-cascade: on receiving `delete`, send `delete`
to all children, wait, then delete yourself. (b) The test data was too
shallow (and too narrow): it needed depth ≥ 2 and width ≥ 2.
Smallest catch: a directory containing a directory containing a file,
asserting the total equals the sum of all leaves.

**A3.** (a) It separates the traversal (iteration over the structure)
from the operation performed at each node. Other operations on the same
walk: find the largest file, collect names matching a pattern, count
nodes, sum permissions violations. (b) You keep the separation — one
traversal, swappable operation. You discard the double dispatch that
lets the operation behave differently per node type without the walker
knowing the types; with a plain function you usually reintroduce that
as an `isinstance` check or accept uniform treatment.

**A4.** (a) There is exactly one file system, but an object language
hands out new instances on request; Singleton creates the handle once,
caches it, and returns the same handle to every later caller. Cost:
everything is coupled to one hidden instance, and tests share mutable
state. (b) Mechanism: test one mutates the shared instance and test two
inherits it, so pass/fail depends on order. Fix: construct the single
logger at the program's top level and pass it in (dependency
injection). Uniqueness is preserved; tests can inject a fake.

**A5.** (a) `pricing` is the strategy; `total` knows only that it will
hand each item to something that returns a number. `sorted(key=...)` is
the same pattern in the standard library — you pass behavior as a
value. (b) Under Strategy, promotion five is one new function plus one
registration; `total` is untouched and its tests still hold. Under the
if-ladder, you edit the function every product change, so every edit
risks the four existing promotions and every edit re-tests them all.

**A6.** (a) At load time: `@retry` is applied when the module is
imported. Afterwards `charge` is bound to `wrapped`, which closes over
the original function. (b) A decorator that stamps the time before and
after the call and writes the difference, applied with `@timed` to each
function. Harder: stack traces and introspection — five layers of
wrappers bury the real frame, and the reported function name is the
wrapper's unless you preserve metadata.

**A7.** (a) 90% of usage came from 10 icons out of 60; the unused 50
cost eye candy/visual clutter, user confusion, maintenance effort,
reliability risk, and attack surface. (b) Procedure: search for all
references (static); instrument it in production for one release to
see if anything calls it (the coconut — "unused" was a knowledge
claim); check who depends on you before removing a published interface
(left-pad — someone else's build is your blast radius); delete in a
single dedicated commit so revert is one command (Goku — the truth you
are deleting may be the only copy, and you want it recoverable).

**A8.** (a) Is the test new, did it fail last time, how long since it
last ran — weighted and combined. Before: about two weeks to get a
verdict. (b) Reorder the suite so recently failed, new, and
long-unrun tests run first, and report failures as they happen rather
than at the end. It does not reduce total compute or total wall clock
for a full green run; it only moves the *information* earlier.

**A9.** (a) A suite covers lines by union — different tests reach
different lines — so coverage reports the union. Many bugs require a
specific *sequence* of lines with state carried along, a conjunction no
single test performs. Mutation coverage = killed / all mutants. Test
strength = killed / mutants actually reached by some test. (b) Order:
first the surviving boundary mutant — add a test at exactly the
boundary value, it is a named, diagnosed gap. Second the six unexecuted
lines — they are why mutation coverage (55%) trails test strength
(78%); either test them or delete them if they are dead. Third, the
78% itself — reached-but-survived mutants mean assertions that do not
check the values they visit.

**A10.** (a) The test asserted a returned list was empty. It was empty
because the branch that would have populated it never ran: the status
string compared was lowercase without an underscore while the real
status was upper case with one. Coverage did not notice because it only
records which lines executed, and the lines it counted did execute —
the assertion's *reason* is invisible to coverage. (b) Shape: (1)
mutation-test one core package and read the survivors — machine work,
no hand reading; (2) grep the suite for assertion-free tests and
assertions on empty/None/trivial values, which is where "passes for the
wrong reason" concentrates; (3) deliberately break one production
behavior and confirm the suite goes red — if it stays green you have
measured the gap directly. A fourth, if there is time: check for tests
whose setup depends on a string literal duplicated from production
code, since that is the exact shape of the bug above.
