## 1. Glossary (debugging, as far as we got)

- **The oracle, the trap under all of it.** An oracle says what is
  right; you fix until it is satisfied. Every method below is
  "contorted by the oracle of pass and fail," and *where you get the
  oracle* is the open problem. "Use an LLM" just moves it: now you
  must test that the LLM-oracle is right, and re-test it whenever the
  code changes.
- **Fault / error / failure.** A fault is a potential error; an error
  is bad state; only when a fault *causes* an error that shows do you
  call it a failure. Many faults never become failures — which is why
  "fix this" / "it won't matter" fills code reviews, and why Unix
  utilities (`ls`, `grep`, `awk`) carry 20–30% never-covered dead
  code.
- **Bohr / Heisen / Mandel bugs.** Bohrbug: solid, same every run
  (Bohr's plum-pudding atom). Heisenbug: changes when observed — add a
  print and it hides. Mandelbug: **deterministic underneath, but its
  cause is so complex — long gaps between fault and failure, reliance
  on accumulated state, timing, or environment — that occurrences look
  random.** Named for Mandelbrot: structure that stays just as tangled
  however far you zoom in. So a Bohrbug you reproduce, a Heisenbug you
  disturb, a Mandelbug you cannot untangle.
- **The debugging loop.** Observe a failure → hypothesize a cause →
  predict → experiment → conclude. Software's advantage: you can
  *rerun*. Ctrl-alt-del gives a fresh patch of soil; a field
  scientist is stuck with soil still contaminated by last
  experiment's fertilizer. (Facebook experiments on itself because
  cloning Facebook means cloning all of human behavior.)
- **Anti-patterns.** Shotgun debugging (change everything, rerun,
  hope); superstition (restart the server twice before the demo);
  the quick-fix reflex (clamp a variable to 0 — now it's self-admitted
  debt and a new bug); blame the platform ("cosmic ray," "works on my
  machine"). The **rubber duck**: explaining the bug line by line
  makes the answer surface mid-sentence.
- **Reproduce first.** No reproduction, no debugging. Keep **config
  under version control** (an industry site kept code versioned but
  could not say which config was live). Keep **seeds** — ship your own
  RNG so asserts hold across Mac/Linux/Windows; low seeds return
  near-zero for a while, so seed with a big integer. **Flaky tests**
  come from the environment (web traffic that differs tomorrow; bad
  solder; the fuzz-testing pioneer who got more crashes during
  thunderstorms hitting the phone line).
- **Delta debugging.** Split the failing input into n chunks (n=2),
  test each and its complement, keep anything smaller that still
  fails with the **same signature**, else go finer (n→2n). Verdicts:
  **PASS** (target crash absent), **FAIL** (crash, same
  type/message), **UNRESOLVED** (some *other* crash, e.g. a syntax
  error — set aside). Binary chop shrinks an 847-char SQL query to a
  tiny crashing string in under two minutes. `git bisect` is the same
  search over commit history. Caveat: assumes failing subsets keep
  failing — paired structures break it, so structure-aware shrinkers
  exist.
- **Spectrum-based fault localization (a Bayesian move).** Colour each
  line: **green** (only passing tests reach it), **red** (only
  failing), **yellow** (on the branch to either). Per line count `ef`
  (failing tests through it) and `ep` (passing); suspicion ≈
  failing-share over the total — the literature has dozens of
  formulas but "most are the same move: reward failing-attendance,
  punish passing-attendance," and most are provably redundant. Limits:
  ubiquitous lines (main, logging) score mid-table but are innocent;
  the whole thing is only as good as the oracle.
- **Bug locality.** Bugs are social animals — the best predictor of
  the next bug is where the last one was. So spend the *slow* methods
  (human review) on the files that already bled.
- **Fix the process, not the code.** Mars Climate Orbiter: JPL went
  from ~5 missions/year (1959–90) to 30–40 under "better, faster,
  cheaper," which meant outsourcing — and a contractor used
  feet/second where the prime used metres/second, checked by nobody.
  Some bugs are organizational diffs.

## 2. Review questions

Exam-style: **(a)** recall, **(b)** analysis or transfer.

**1. The oracle.**
(a) Why is the oracle called the trap under all of debugging?
(b) A teammate proposes an LLM as the pass/fail oracle for a
localization run. Give the two obligations that creates, and say
what has to happen every time the code changes.

**2. Fault / error / failure.**
(a) Define all three, and say which one a code review argues about
when it says "this won't matter."
(b) `ls`/`grep`/`awk` carry 20–30% never-covered code. Give one
reason that is defensible and one reason it is a risk.

**3. The bug zoo.**
(a) Distinguish Bohrbug, Heisenbug, Mandelbug.
(b) Adding a print makes a crash vanish. Name the species, give two
causes, and the next experiment that separates them.

**4. Spectrum localization.**
(a) What do green, red, and yellow lines mean, and what two counts
drive a line's suspicion?
(b) The literature has dozens of suspicion formulas. Explain why
"most are the same move," and why the top-ranked line is often an
innocent one like `main`.

**5. Process, not code.**
(a) What organizational change preceded the Mars Climate Orbiter
loss, and what was the un-checked assumption?
(b) "Bugs are social animals." Turn that into a policy for where to
spend expensive human review, and justify it.

## 3. Answers, briefly

**A1.** (a) Every method only tells you *where control went* relative
to a pass/fail label; it cannot supply the label, and without a
correct label the whole analysis is "contorted." (b) You must test
that the LLM-oracle is right (a commissioning step), and keep testing
it — re-validate the oracle every time the code changes, or it drifts.

**A2.** (a) Fault = latent defect; error = bad internal state;
failure = observable wrong behaviour. Reviews argue over faults that
may never reach failure. (b) Defensible: untriggered code genuinely
never fails, so effort spent elsewhere is rational. Risk: "never
covered" is a claim about your tests, not the world — a rare real
condition can light it up, and dead code is attack surface.

**A3.** (a) Bohrbug: deterministic, same every run. Heisenbug: shifts
when observed. Mandelbug: chaotic-looking from tangled causes. (b)
Heisenbug; causes e.g. a race or uninitialized memory whose timing
the print perturbs; experiment: compare debug vs release builds (or
add the *already-present* logging), since the difference is evidence
about the cause.

**A4.** (a) Green = reached only by passing tests; red = only by
failing; yellow = on the branch leading to either. Counts: failing-
attendance `ef` and passing-attendance `ep`. (b) They all reward `ef`
and punish `ep`, differing only in how hard; many are provably
rank-equivalent. `main`/logging lines are executed by every test, so
they ride high on attendance while being innocent plumbing.

**A5.** (a) "Better, faster, cheaper" pushed JPL from ~5 to ~30–40
missions/year, forcing outsourcing to contractors; the un-checked
assumption was units — feet/s vs metres/s across the contractor/prime
seam. (b) Failure mass concentrates, so rank files by prior bug count
and point the slow, expensive methods (human review, deep analysis)
at the hottest files; the cheap methods cover the rest.
