## 1. Glossary

### 1.1 The V-model: every build claim needs a matching test

- **V-model** — move down from requirements → design → modules →
  code, then climb back through unit → integration → system →
  acceptance tests. Each test level checks the artifact opposite it.
- **Unit test** — one function or class in isolation. No database,
  network, or neighboring subsystem unless the unit itself owns that
  behavior.
- **Integration test** — checks whether components agree on the
  interface between them. This is where hidden assumptions such as
  units, formats, protocols, or schemas collide.
- **System test** — checks the full product path end-to-end: e.g., add
  item → checkout → payment → confirmation.
- **Acceptance test** — asks whether the built system satisfies the
  customer's requirement, not merely whether the code behaves as
  implemented.
- **Verification** — *did we build the system right?*
- **Validation** — *did we build the right system?*
- **Alpha / beta / A/B** — testing continues after coding: internal
  users, external volunteers, then controlled population splits.
- **Brooks' budget warning** — in the lecture notes' breakdown, about
  half the schedule is testing. Testing is not the cleanup step after
  implementation; it owns a large fraction of the project budget.

### 1.2 Where tests come from

- **Black-box testing** — derive tests from the specification without
  looking at the implementation. Ask what inputs are valid and what
  externally visible behavior the contract promises.
- **Grammar-based generation** — encode the input language as a
  grammar and sample valid inputs from it. Useful when the legal input
  space is too large to enumerate by hand.
- **Coverage-guided generation** — bias future generated inputs toward
  grammar choices that reach new code. The generator learns where
  unexplored behavior lives.
- **White-box testing** — derive tests from implementation structure:
  branches, states, transitions, and control flow.
- **State-machine test** — draw the states and arrows, then demand a
  test for each transition. The diagram often exposes missing
  requirements before the test even runs.

### 1.3 Coverage: useful alarm, weak guarantee

- **Line / statement coverage** — which executable lines were visited
  by the suite.
- **Branch coverage** — whether each decision outcome was taken.
- **Path interaction** — the combinations of branches taken together.
  Two tests can achieve 100% line and branch coverage and still miss a
  meaningful cross-branch case.
- **The lecture example** — `example(1,1)` plus
  `example(-1,-1)` reaches every line and every branch, but never
  checks `x > 0` with `y < 0`.
- **Smoke-alarm rule** — low coverage is evidence that something is
  wrong with the suite. High coverage is not evidence that the suite
  is strong.

### 1.4 Mutation testing: test the tests

- **Mutation testing** — deliberately modify the program with small
  bugs, then ask whether the existing test suite notices.
- **Mutant** — one deliberately changed version of the program.
- **Mutation operator** — a small syntactic change such as arithmetic
  replacement (AOR), relational replacement (ROR), or constant
  replacement (CR).
- **Killed mutant** — at least one test fails after the mutation.
- **Surviving mutant** — all tests still pass. Either the suite missed
  the changed behavior, or the mutation is equivalent.
- **Mutation score** — `killed mutants / total mutants`.
- **Equivalent mutant** — changed syntax with unchanged semantics. No
  correct test can kill it, which is one reason mutation score is not
  a perfect oracle.
- **What mutation adds over coverage** — coverage asks *did the tests
  visit this code?* Mutation asks *would the tests complain if this
  code were wrong?*

### 1.5 Testing when the answer is unknown

- **Oracle problem** — many useful inputs do not come with a known
  correct output, so a normal assertion cannot simply say
  `actual == expected`.
- **Differential testing** — run the same input through independent
  implementations of the same specification and compare their
  behavior. A disagreement says at least one implementation is wrong;
  it does not automatically say which one.
- **Shadow testing** — run a new implementation beside an old one on
  the same workload, without letting the new version control the user
  result. Compare the outputs.
- **Metamorphic testing** — when exact outputs are unknown, test a
  relation that should remain true across transformed inputs. Example:
  adding a stricter hotel filter must not increase the result count.
- **Metamorphic relation** — the property used as the indirect oracle:
  refund ≤ payment, filtering cannot increase count, sorted output is
  a permutation of input, etc.

### 1.6 Regression at scale

- **Regression suite** — accumulated tests protecting behavior that
  already worked before the latest change.
- **Test prioritization** — order the suite so likely or informative
  failures appear early rather than waiting hours for the whole suite.
- **Useful signals from the notes** — recently failed, not run in a
  while, or covers new functionality.
- **APFD** — average percentage of faults detected; a way to reward a
  test order that exposes faults earlier.
- **All-pairs testing** — reduce a combinatorial configuration space by
  covering every pair of parameter values instead of every complete
  combination.
- **Flaky test** — passes and fails without a relevant code change,
  often due to timing, networks, test order, or unseeded randomness.
- **The real flakiness cost** — not one annoying red build. It trains
  developers to distrust red builds, which destroys the suite as a
  decision signal.

### 1.7 Project 2 rule

- **The rubric watches history** — CI green from day one, tests arriving
  with features, issues moving, and the repository staying healthy.
  A heroic cleanup in the final week is not the same artifact.
- **Your 1a tests are inherited assets** — move them into Project 2 and
  turn them into the first regression safety net.
- **LLM-generated tests still need testing** — many green tests and high
  coverage can still mean weak assertions. Mutation testing is one way
  to audit whether generated tests actually detect wrong behavior.

## 2. Beyond the notes

### 2.1 The V-model as a loop, not a waterfall museum piece

The lecture used the V-model less as a historical process diagram and
more as a discipline for small chunks of work. The important idea is:
**every claim made while going down the left side creates an obligation
on the right side.**

For a small feature:

1. State what the feature must do.
2. Decide how it fits the design.
3. split it into modules and code.
4. Unit-test the code.
5. Integration-test the module seams.
6. System-test the whole path.
7. Check the result against the original requirement.

The lecture connected this to coding agents: an agent can work in
small **micro-sprints** where each subproblem gets its own miniature
V. The point is not that the agent follows a pretty diagram. The point
is that generated code arrives with matching checks at several levels,
so mistakes do not accumulate silently.

### 2.2 Integration testing is where assumptions become executable

The simplest lecture example was units: one component thinks in
meters, another in centimeters. Each component can be locally correct
and the system can still be wrong.

That is the deeper meaning of an integration test. It does not merely
mean "call two functions at once." It asks whether assumptions made on
one side of an interface are the same assumptions made on the other:

- units and scale;
- field names and schemas;
- error codes;
- ordering;
- time zones;
- nullability;
- protocol versions.

Unit tests can prove both halves work exactly as written and still miss
this class of failure. Integration tests are where the lies in the
interfaces meet.

### 2.3 Black box and white box answer different questions

The lecture's short distinction is worth keeping:

- **Black box:** I know what is expected, but I do not care how it is
  implemented.
- **White box:** I know what is inside, so I force the program through
  the important states and branches.

Neither dominates the other. A white-box suite can perfectly traverse
an implementation that misunderstood the requirement. A black-box
suite can correctly test the contract while missing an internal state
transition that only appears after a rare sequence of events.

The useful move is to let the two views disagree with each other. The
spec tells you what behavior must exist; the structure tells you where
that behavior can hide.

### 2.4 Why 100% coverage can still miss the bug

The `x,y` example is small enough to remember for an exam.

```python
def example(x, y):
    a = x + y
    if x > 0:  b = a*2
    else:      b = a*3
    if y > 0:  c = b+a
    else:      c = b-a
    return c
```

Two tests, `(1,1)` and `(-1,-1)`, can visit every line and both sides of
both `if`s. Yet the suite never checks the mixed-sign paths.

So coverage counts **where control went**, not whether the suite
checked the right relationships while it was there. That is why high
coverage plus weak assertions can look excellent on a dashboard while
missing obvious regressions.

A useful hierarchy:

- low coverage → definitely inspect the suite;
- high coverage → good, now ask harder questions;
- high mutation score → stronger evidence that assertions notice
  wrong behavior;
- none of the above → proof that the software has no bugs.

### 2.5 Mutation testing turns "good tests" into an experiment

Without mutation, "this is a good test" is often a feeling. Mutation
creates a controlled experiment:

> If I damage the program in a small, plausible way, does the suite
> detect it?

Suppose the original is:

```python
if price > 100:
    return price - price * rate
```

Three mutations ask three different questions:

| mutation | what a survivor suggests |
|---|---|
| `price / rate` | assertion does not verify the amount |
| `price >= 100` | boundary at exactly 100 is missing |
| `price > 50` | middle region is not exercised |

The surviving mutant is therefore not just a score penalty. It is a
clue about the disease in the suite.

### 2.6 Mutation's bill: CPU, combinatorics, and equivalent mutants

The lecture emphasized the cost more strongly than the compact notes.
A single function admits many one-token changes. A large codebase
admits enormous numbers of mutants, and every mutant wants another
suite run.

So mutation testing has its own search problem:

- Which files deserve mutation first?
- Which mutation operators matter for this code?
- How many mutants can the CI budget afford?
- Which survivors are real missed bugs versus equivalent mutants?

That makes mutation testing a **tool for spending testing budget more
intelligently**, not a commandment to mutate every token after every
commit.

### 2.7 Differential testing: disagreement is a cheap oracle

The lecture used compilers to build the intuition. If two systems claim
to implement the same language specification, feed both the same
program. You may not know the correct result yourself, but agreement is
expected; disagreement is suspicious.

The important subtlety: differential testing gives you an alarm, not a
judge. If implementation A says 7 and implementation B says 9, the diff
has found something worth investigating, but the diff alone does not
identify the guilty implementation.

Grammar-based input generation fits naturally here: the grammar creates
large numbers of valid test programs, requests, or structured inputs;
the differential oracle tells you where implementations diverge.

### 2.8 Shadow testing: compare the future against the known past

The lecture framed shadow testing as a practical cousin of differential
testing. Instead of comparing two independent vendors, compare your
**new implementation** with your **old implementation** on the same
workflow.

The old system serves the user. The new system runs silently beside it.
Then diff the outputs.

This is especially useful during refactors and rewrites because the new
system can be exercised on realistic traffic before it is trusted with
real decisions. The limitation is obvious but important: if the old
system is wrong, matching it reproduces the wrong behavior.

### 2.9 Metamorphic testing: when you know the rule but not the answer

The hotel example captures the idea:

- Query A: all hotels in Sydney → 1,671.
- Query B: Sydney hotels, 4-star+.
- You may not know whether 1,671 is globally correct.
- But Query B returning 1,800 violates a relation you *do* know:
  filtering cannot increase the count.

Metamorphic testing changes the oracle question from:

> "What exact answer should this input produce?"

into:

> "How should the answer change when I transform the input?"

That is often much easier to state, and those relations can survive
changes to the implementation better than example-by-example expected
outputs.

### 2.10 All the clever testing methods still hit the budget wall

Mutation creates many altered programs. Differential fuzzing creates
many inputs. Shadow testing duplicates work. Metamorphic testing adds
follow-up inputs. Large regression suites accumulate forever.

Eventually the question becomes not "can we test this?" but:

> **Which test should run first if I cannot afford to run everything
> now?**

The lecture's intuition was signal latency. If a cheap, fundamental
test can tell you after two minutes that the change is broken, there is
little value in waiting five hours to learn the same thing from test
#40,000.

This is why prioritization is part of testing, not merely CI plumbing.
The order in which evidence arrives changes developer feedback time and
compute cost.

### 2.11 Flakiness spends the team's trust

A flaky test is harmful because it changes human behavior.

First failure: investigate.

Fifth unexplained failure: rerun CI.

Fiftieth: ignore red.

At that point the repository can contain excellent deterministic tests
and still have a broken safety signal, because developers have learned
that red often means nothing. The lecture's practical point is that
flakiness should be isolated and repaired quickly. "Just rerun it" is
not neutral; every rerun teaches the team to trust the suite less.

### 2.12 The testing ladder for an LLM-generated suite

The notes and lecture together imply a useful sequence for generated
tests:

1. **Run them.** Do they even execute?
2. **Read the assertions.** Are they checking behavior or only
   `not None`-style trivia?
3. **Measure coverage.** What code is untouched?
4. **Mutate the implementation.** Do the generated tests detect wrong
   behavior?
5. **Check oracle independence.** Did the model merely copy the same
   mistaken logic into both implementation and expected result?
6. **Add differential or metamorphic checks** where exact expected
   outputs are difficult.
7. **Watch runtime and flakiness.** A suite nobody trusts or can afford
   to run is not protection.

The course's recurring theme shows up again: generation is cheap;
**evaluation is the engineering problem.**

## 3. Review questions

Ten questions, ~7 minutes each. **(a)** recall, **(b)** analysis or
transfer. Each part gives you some of the answer; supply the rest.

**1. The V-model**  
(a) Put these in the correct matching pairs: requirements, design,
modules, code, unit test, integration test, system test, acceptance
test. Then state the difference between verification and validation.  
(b) Pick one feature from your Project 2 product. Write one artifact on
the left side of its mini V and the matching test on the right side.

**2. Unit vs integration**  
(a) A discount function returns the correct value in isolation. Name the
test level that proved that. The checkout passes that value to a payment
service that interprets dollars as cents. Name the test level that
should catch the second failure.  
(b) Name two assumptions crossing one interface in your project that
could be locally correct on both sides and globally wrong.

**3. Black box vs white box**  
(a) A tester writes cases only from the API contract and never reads the
source. Which style? Another tester draws five state transitions and
writes one test per arrow. Which style?  
(b) Give one bug that the first style is better positioned to catch and
one bug that the second style is better positioned to catch.

**4. Coverage**  
(a) Why do `(1,1)` and `(-1,-1)` achieve 100% line and branch coverage
in the lecture example yet still leave behavior untested?  
(b) A pull request reports 98% line coverage. Give two questions you
must still ask before claiming the suite is strong.

**5. Mutation testing**  
(a) Define mutant, killed mutant, surviving mutant, mutation score, and
equivalent mutant.  
(b) Your suite has 95% line coverage but only a 55% mutation score. Give
three likely weaknesses in the suite and one concrete next test you
would add for each.

**6. Oracle problem and differential testing**  
(a) What is the oracle problem? How does differential testing avoid
needing an exact expected output for every input?  
(b) Two implementations disagree. State exactly what you know and what
you still do **not** know.

**7. Shadow and metamorphic testing**  
(a) Distinguish shadow testing from differential testing between two
independent implementations. Then define a metamorphic relation.  
(b) Write two metamorphic relations for your Project 2 product. They
must state how outputs should change, or not change, after an input
transformation.

**8. Testing under a compute budget**  
(a) Why can mutation, differential, and large regression testing become
expensive even when each individual test is simple?  
(b) Your full suite takes six hours. Name three signals from the notes
that could move a test earlier in the order, and explain why early
failure detection changes the engineering cost.

**9. Flaky tests**  
(a) Name four common sources of flakiness. Why can a flaky test be worse
than no test?  
(b) A teammate says, "CI failed because of the network test; rerun it."
State a policy for what the team should do today and what must happen
within the week.

**10. Testing LLM-written tests**  
(a) An LLM writes 40 green tests and coverage rises to 95%. Why is that
still weak evidence of suite quality? Name the technique from this
lecture that directly tests whether those tests notice broken code.  
(b) Design a cheap three-step audit for generated tests in your project.
Each step must answer a different question about suite quality.

## 4. Answers, briefly

Part (b) often depends on your own project. What matters is the shape:
a concrete test target, a concrete failure, and a reason that test
level or technique can expose it.

**A1.** (a) `code ↔ unit`, `modules ↔ integration`,
`design ↔ system`, `requirements ↔ acceptance`. Verification asks
whether we built the system right; validation asks whether we built the
right system. (b) Shape: requirement such as "a user can cancel an
order before dispatch" paired with an acceptance/system test that
creates an order, cancels it, and verifies the externally visible
result.

**A2.** (a) Unit test first; integration test second. The individual
pieces can both satisfy their own local rules while disagreeing on the
interface. (b) Good answers name actual contracts: dollars vs cents,
UTC vs local time, `user_id` string vs integer, nullable vs required,
status `done` vs `completed`.

**A3.** (a) Contract-only = black box. State/transition-driven = white
box. (b) Black box is strong against "implemented the wrong contract."
White box is strong against "rare internal branch/state never
exercised." Neither replaces the other.

**A4.** (a) Coverage records each line/branch being visited somewhere;
it does not require every meaningful combination of decisions. The
mixed-sign paths remain absent. (b) Ask: are assertions strong enough?
Are important branch combinations/boundaries covered? What is the
mutation score? Are important requirements tested end-to-end?

**A5.** (a) Mutant = deliberately changed program; killed = suite fails;
surviving = suite stays green; score = killed/total; equivalent =
semantic behavior did not change, so no valid test can kill it. (b)
Likely diseases: weak assertions, missing boundaries, missing behavior
regions/interactions. Medicine: assert exact discount value, test
exactly `price == 100`, test values in the 50–100 or mixed region that a
surviving mutant exposes.

**A6.** (a) Oracle problem: exact correct output is unavailable or too
expensive to know. Differential testing compares implementations that
should obey the same specification and flags disagreements. (b) You
know at least one observed behavior differs and therefore deserves
investigation. You do not know which implementation is wrong, whether
both are wrong in different ways, or what the correct output is.

**A7.** (a) Shadow testing usually compares a new version of *your own*
system against the currently trusted version on the same workload;
differential testing more generally compares implementations of a
shared spec. A metamorphic relation states a property connecting the
outputs of related inputs. (b) Shape: add a filter → result count cannot
increase; add an item with positive price → cart total cannot decrease;
retry an idempotent read → stored state must not change.

**A8.** (a) The multiplicative count is the problem: many mutants × full
suite, many generated inputs × several implementations, or years of
regression tests. (b) Move forward tests that failed recently, have not
run in a while, or cover new functionality. Earlier signal means less
CI compute wasted after a known-bad change and less developer time
blocked waiting for feedback.

**A9.** (a) Timing, network behavior, test-order dependence, and
unseeded randomness. The deeper cost is learned distrust: developers
start treating red as noise. (b) Quarantine the flaky test immediately
so its noise is explicit; diagnose and fix it, or remove/replace it,
within the week. Do not make repeated reruns the normal workflow.

**A10.** (a) Green + coverage says the tests execute code; it does not
show that assertions reject incorrect behavior. Mutation testing is the
direct audit. (b) Example: inspect assertion strength → measure
coverage/gaps → mutate one core function and inspect survivors. A
stronger version then adds one metamorphic or differential check where
the expected output is difficult to write manually.
