## 1. Glossary

### 1.1 Maintenance, defined and divided

- **Maintenance.** Most of the life of software. Maintainers spend
  about half their time *reading* code — the writing is the small end
  of the funnel. A maintainer does not boast of being a fast coder;
  a maintainer is a fast *understander*.
- **The four kinds.** **Corrective** (fixing faults users found —
  only ~20% of the historical record); **adaptive** (the environment
  moved: new OS, new API, new tax law); **perfective** (the system
  succeeded, so people want small changes to its behavior — the
  biggest share); **preventive** (nothing is broken; you repay debt
  now to head off trouble later). The surprise: maintenance is
  mostly *not* bug-fixing. It is the price of success.
- **Lehman's laws.** *Continuing change* — a used system must change
  because its world changes. *Increasing complexity* — structure
  decays unless effort is spent specifically to rein it in ("a big
  pile of dung collapsing into dust; your mission is to keep the
  dust from spreading"). *The system shapes its users* — insurance
  staff sell the policies the software can represent. *Continuing
  growth* — features only accumulate, because deleting one angers
  someone.
- **The running system is the spec.** Nobody has a current written
  specification of a decades-old system; a thousand maintenance
  steps separate it from whatever was written down in 1968. Its
  behavior — including quirks and bugs — is the only spec there is.

### 1.2 COBOL (the longest-running maintenance experiment)

- **COBOL.** Shipped 1959; Admiral Grace Hopper's team. Design bets:
  English-like readability (a language for everyone, where Fortran
  was for scientists) and portability. Old-fashioned to modern eyes
  — data divisions, global variables — and still running hundreds of
  billions of lines supporting trillions in daily commerce. By some
  accounts at least half of card transactions pass through COBOL
  somewhere (the popular "95%" figure resists fact-checking; "at
  least half" survives it). Not even Lisp is as old.
- **Why it survives.** It is genuinely good at its job (fixed
  formats, indexed files, native decimal arithmetic — exactly a
  bank's workload); and the economics flipped: replacing manual
  labor with software paid hugely, but replacing a working system
  with a slightly faster one pays almost nothing and risks
  everything. 92% of using organizations call it strategic; many
  expect to run *more* next year. The supply of COBOL programmers is
  literally a nationally monitored number.
- **Replacement disasters.** Commonwealth Bank of Australia: five
  years, ~A$1B, legendary overruns — and that is the success story.
  TSB 2018: customers locked out for weeks, some seeing other
  people's accounts, ~£300M plus ~£50M fraud. New York Times:
  COBOL→Java worked, but blew the schedule proving the new system
  reproduced *every* old behavior.
- **Y2K, reframed.** Not a dodged disaster — the greatest
  *successful* maintenance project in history: ~$320B spent
  worldwide, and the non-event was the purchase.
- **The COVID surge.** New Jersey, 2020: 1,600% spike in
  unemployment claims; the governor on television begging for COBOL
  volunteers; Congress wrote a flat $600 into the CARES Act because
  states said changing a *percentage* would take five months.

### 1.3 Technical debt

- **Technical debt.** Not bad code — a *loan*. You shipped before
  the work was done, and you pay interest (every change costs
  extra) until you repay the principal (do the deferred work).
- **Self-admitted technical debt (SATD).** TODO / FIXME / HACK / XXX
  comments — the author confessing the loan in writing. Roughly 20%
  of fielded code carries such comments. A one-minute grep is a
  debt audit written for you by the borrowers themselves.
- **The kinds.** **Code debt** (duplication — a fix lands in one
  copy and misses the others; God classes; dead code — which sounds
  safe until an attacker exploits the code nobody watches). **Test
  debt** (missing tests; asserts that rarely trigger; flaky tests;
  elaborate suites too slow for anyone to run). **Documentation
  debt** (docs that drifted from the code, with no warning that
  they did). **Dependency debt** (left-pad: a tiny package removed,
  the internet breaks; xz: a two-year social-engineering campaign
  ending with a hostile maintainer holding root on every distro).
  **Configuration debt** (next section).
- **Repayment policy.** The boy-scout rule ("always leave the code
  cleaner") was dismissed from the podium as "never going to
  happen." What was endorsed: *priced* repayments — debt is an
  emergent property of programming, you will never clear it, so
  spend repair effort only where the interest is highest.

### 1.4 The configuration abyss

- **The knobs paper.** "Hey, you have given me too many knobs"
  (FSE 2015): option counts only ever grow (MySQL's doubled
  1999–2014; Apache's quadrupled); most parameters are touched by
  nobody; up to half of cloud-software outages trace to
  configuration error, not code error.
- **The debt's birth certificate.** A real HDFS developer
  discussion: unsure what a good value is → "how about making it
  configurable?" → field study finds no user who ever set it. A
  knob is a decision the developer declined to make, exported to
  every user.
- **The scale.** SQLite's makefile options multiply out to ~3
  billion configurations — and they affect speed and energy.
  Three hundred boolean options give 2^300 configurations; the
  observable universe holds ~10^27 stars. Your software's
  configuration space is bigger than the space around it.
- **Nobody versions the config.** Industrial observation: teams
  keep application code under git but leave the configuration
  files that control their cloud services unversioned —
  the code that most often takes production down is the code
  least studied.
- **Even the checkers have knobs.** Amazon runs a theorem prover
  over uploaded permission files to verify security settings. The
  prover itself has ~420 configuration options — over half marked
  "advanced user only."

### 1.5 Modernization vocabulary

- **Reverse engineering** — recover the design; produces
  understanding; changes nothing. **Refactoring** — change the
  structure, never the behavior. **Re-engineering** — reverse
  engineer, then rebuild forward. **Migration** — new platform,
  language, or architecture; behavior held constant. People blur
  these; exams will not.
- **The portfolio quadrant** (business value × technical quality):
  low/low → replace with something off the shelf; high value/low
  quality → re-engineer; high/high → evolve carefully; low
  value/high quality → maintain but do not extend; and when new
  technology is the point → migrate.
- **The big migration of this decade: on-prem → cloud.** You cannot
  lift-and-shift: the cloud's scalability only arrives if the
  application is chopped into small pieces that can be duplicated
  across nodes on demand (Black Friday = copy the software and
  stand up more). That chop is a massive refactor, not a move.
- **Shadow testing, with teeth.** The old system serves users; the
  new one runs silently on the same traffic; diff the outputs.
  Amazon ran one rewrite for a month — ~7 *billion* runs — and
  shipped only when the outputs were byte-identical to the old
  system. Note what byte-identical means: old bugs faithfully
  reproduced, on purpose.
- **Port the quirk.** Downstream systems depend on the old system's
  quirks, so the rule of thumb is: move the quirk across, fix it
  later if ever. Mid-migration, the question "am I fixing a bug or
  breaking a dependent?" has no cheap answer — which is also why
  you never mix migration with mass repair in one step.
- **Anti-corruption layer.** Old and new systems speaking different
  vocabularies ("tax" vs "rebate") talk through a translator — the
  adapter pattern doing border control. And Parnas's
  interface-first discipline gives the swap mechanism: wrap the old
  component in an interface, point everyone at the interface, and
  exchange internals behind it.

## 3. Review questions

Exam-style: **(a)** recall, **(b)** analysis or transfer.

**1. The four kinds.**
(a) Name the four kinds of maintenance and give the rough share of
effort that fixing faults actually takes.
(b) "Maintenance is mostly the price of success, not the cost of
failure." Defend that claim using two of the four kinds, then name
the one kind that an overworked team always cuts first and the
long-term cost of cutting it.

**2. COBOL economics.**
(a) Give two reasons COBOL survives that have nothing to do with
laziness or nostalgia.
(b) The first automation of a bank's ledgers paid for itself
hugely; rewriting that COBOL in a modern language usually does not.
Explain the economic asymmetry, and name the 2018 migration whose
customers saw strangers' accounts.

**3. The running system is the spec.**
(a) State the course's claim about correctness in mature systems,
and say what "small deltas" means as a change policy.
(b) The New York Times ported quirks of its old COBOL system into
the new Java system on purpose. Using "the running system is the
spec," justify that choice — then describe the situation in which
porting a quirk is the *wrong* call, and the record you should
write either way.

**4. Y2K.**
(a) What was the Y2K bug, and roughly what was spent worldwide
fixing it?
(b) "Y2K was a non-event, so the money was wasted." Attack that
argument using this week's framing of maintenance, and name one
present-day expenditure that is the same purchase wearing new
clothes.

**5. Technical debt.**
(a) Define technical debt via interest and principal, define SATD,
and give the one-minute way to measure SATD in a repo.
(b) The boy-scout rule ("always leave code cleaner than you found
it") was dismissed in class as unrealistic. Give the argument for
dismissing it, state the policy endorsed instead, and apply that
policy to an inherited repo with 200 TODO comments: which ones get
paid, and how do you choose?

**6. Knobs.**
(a) What did the HDFS developers do when they did not know a good
value for a parameter, and how many users did the researchers later
find for it?
(b) A teammate defends 38 config options with "they all have
sensible defaults, so they cost nothing." Using this week's
evidence — outage causes, the unversioned-config observation, and
the advanced-user-only theorem prover — price the real carrying
cost of a knob nobody sets.

**7. Configuration spaces.**
(a) Roughly how many configurations do 300 boolean options
generate, and how does that compare to the number of stars in the
observable universe?
(b) "Fly what you test" (test the artifact you ship) was a course
rule from architecture week. Explain why a 300-knob system makes
that rule unsatisfiable as stated, and what testing-week technique
(sampling pairs of options rather than all combinations) rescues a
weaker version of it.

**8. Migration machinery.**
(a) Distinguish reverse engineering, refactoring, re-engineering,
and migration in one sentence each.
(b) Amazon ran a rewrite in shadow for a month — billions of runs —
and shipped only on byte-identical output. Say what byte-identical
buys, what it deliberately preserves that a "better" system would
fix, and why lifting an on-prem application unchanged onto the
cloud forfeits the cloud's main benefit.

**9. The portfolio quadrant.**
(a) Name the five options on the modernization quadrant (business
value × technical quality) and the action each one prescribes.
(b) Place your inherited proj2 on the quadrant, justify the
placement with one measurement from your triage, and say what the
placement forbids you from doing this month.

**10. Dependency debt.**
(a) Define dependency debt, and give the left-pad and xz examples
in one line each.
(b) "75–95% of a modern system is code you downloaded." Explain why
that makes dependency debt a security problem, not just a
maintenance one, and give one check you would run on your inherited
repo's dependencies in week one.

## 4. Answers, briefly

**A1.** (a) Corrective (~20%), adaptive, perfective (the biggest
share), preventive. (b) Perfective and adaptive dominate: change
requests arrive *because* people use the system and *because* its
world moves — both are symptoms of success. Preventive gets cut
first (nothing is visibly broken); the cost is Lehman's complexity
law compounding until every later change costs more — deferred
structure-repair is a loan at rising interest.

**A2.** (a) Any two: it is genuinely fast at its exact workload
(fixed formats, indexed files, decimal arithmetic — no float
rounding on money); replacement is ruinously expensive and risky;
the surrounding staff, process, and downstream systems are tuned to
it. (b) Automation #1 replaced armies of manual clerks — enormous
return. A rewrite replaces a working fast system with another
system of roughly equal speed: cost and risk up front, payoff near
zero, and tail risk catastrophic. TSB.

**A3.** (a) Correctness is not absolute: mature systems are "kind
of broken" with downstream dependents on the broken parts, so the
running system is the de facto spec; change safely by making small
deltas from current behavior. (b) Port the quirk: downstream
consumers may depend on it, and mid-migration you cannot cheaply
tell bug from load-bearing behavior — so preserve first, fix later
as its own change. Wrong call when the quirk is a genuine hazard
(corrupting data, security hole) whose preservation harms users
faster than its removal breaks dependents. Either way, write the
decision down: quirk, choice, reason — the next maintainer must
know it was deliberate.

**A4.** (a) Two-digit years made "00" compare less than "99";
~$320B spent worldwide. (b) The non-event was the *product
purchased*: the spend is why planes did not fall. Judging
prevention by the absence of disaster is a selection error — the
counterfactual was never free. Same purchase today: preventive
maintenance generally, or the month of byte-identical shadow runs
before a cutover — money spent so that nothing visible happens.

**A5.** (a) Debt = shipping before the work is done; interest =
every change costs extra while the gap persists; principal = the
deferred work. SATD = the developer confessing in comments.
Measure: grep for TODO/FIXME/HACK/XXX. (b) Dismissal: cleanup on
every touch is a tax nobody sustainably pays, and most debt sits
in code you never revisit, charging no interest. Endorsed: priced
repayment — repay where interest is highest. For the 200 TODOs:
cross-reference with churn; pay the ones sitting in files you
change weekly and on the critical path; leave the rest recorded in
the ledger.

**A6.** (a) Unsure of a good value, they made it configurable and
shipped a default; the field study found no user who had ever set
it. (b) Each unset knob is: documentation to maintain, a dimension
in the test matrix nobody tests (so fielded configurations are
untested by construction), a hiding place for the
misconfiguration class that causes a large share of cloud outages,
attack surface, and — per the unversioned-config observation —
often sits in files with no history, so when it does bite there is
no archaeology. "Has a default" prices the happy path only.

**A7.** (a) 2^300, versus ~10^27 stars — the configuration space
dwarfs the visible universe. (b) You cannot test what you fly when
"what you fly" is one point in 2^300; almost every fielded
configuration is untested by construction. All-pairs (covering
every *pair* of option values rather than every combination)
restores a bounded promise: every two-way interaction has been
exercised — far weaker than the original rule, and usually the
best rule arithmetic allows.

**A8.** (a) Reverse engineering recovers understanding, changes
nothing. Refactoring changes structure, never behavior.
Re-engineering reverse-engineers then rebuilds forward. Migration
changes platform/language/architecture holding behavior constant.
(b) Byte-identical buys certainty that no downstream consumer can
tell the difference — and deliberately preserves old bugs and
quirks, because the old system is the spec. Lift-and-shift
forfeits scalability: the cloud pays off when the application is
small pieces that can be duplicated across nodes under load, and a
monolith cannot be duplicated piecewise — the chop is a refactor
you cannot skip.

**A9.** (a) Low value/low quality → replace off the shelf; high
value/low quality → re-engineer (keep the rules, pay the debt);
high/high → evolve carefully; low value/high quality → maintain but
do not extend; new technology the point → migrate. (b) Shape: name
a quadrant, back it with one triage number (coverage, churn, build
health), and name the forbidden move — e.g. "high value, low
quality → re-engineer, so this month forbids a from-scratch rewrite
and forbids bolting on features before the debt is paid."

**A10.** (a) Dependency debt: the maintenance liability of code you
pull in — pinned ancient versions, abandoned upstreams, unchecked
licenses. left-pad: an eleven-line package the author pulled,
breaking a swath of the internet. xz: a two-year social-engineering
campaign that handed a hostile maintainer root on every distro. (b)
If most of your system is downloaded, your attack surface is
everything you wrote *plus* everything you pulled, and a dependency
can turn malicious (xz) or vanish (left-pad) without you touching a
line — Equifax was an unpatched dependency CVE. Week-one check: list
the dependencies, flag the ones that are unpinned, abandoned, or
carry an incompatible license, and run a vulnerability scan against
the lockfile.
