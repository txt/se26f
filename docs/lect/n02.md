Recall N1's picture: classic SE keeps a loop between planning and
testing. Tonight is that loop, made concrete:

- **Use cases are the plan.** They state what the system should do,
  as checkable expectations.
- **Tests are the check.** They compare expectation to reality, one
  run at a time.
- When a test surprises you, the use case gets better. When a use
  case is vague, the test exposes it. That two-way traffic is the
  whole method.

## 0. Use cases: writing down what should happen (60 min)

A use case is one actor chasing one goal through your system, written
as numbered steps. The format, in full, with five worked examples:
[usecases0.md](../submit/1/usecases0.md). That file is the contract
for D2. Tonight we cover why each part exists.

Know the aim before you start. Twenty use cases is not a complex
spec, and you are not writing one. The aim is two things:

- **Breadth, not depth.** A breadth-first sweep across the whole
  system — every actor, every major goal, one page each — so no big
  region of the code goes unexamined. Wide and shallow beats one
  corner specified to death.
- **Something you can show a user.** A use case is written in the
  actor's language, so a stakeholder can read it and say "yes, that's
  what I do" or "no, step 4 is wrong." Code cannot get that reaction;
  use cases can. They are a communication tool first, a spec second.

### The parts, and why

| Part | Why it exists |
|---|---|
| **Name** | Verb + noun, the actor's goal ("Place order"). Forces you to say who wants what. |
| **Primary actor** | No actor, no requirement — just a feature nobody asked for. |
| **Stakeholders & interests** | Others care too: the restaurant wants accurate orders, the platform wants no fraud. Conflicts live here. |
| **Preconditions** | What must already be true. These become your test setup. |
| **Trigger** | The event that starts it. This becomes your test's first action. |
| **Main success scenario** | Numbered steps, actor ↔ system, happy path only. No ifs. |
| **Extensions** | Every branch and failure, keyed to steps ("4a: payment declined → ..."). |
| **Postconditions** | True on success. These become your test's assertions. |

Two rules do most of the work:

1. **The main scenario stays clean.** All branching lives in the
   extensions. That separation is the whole trick — a use case with
   ifs in the main path is a flowchart wearing a costume.
2. **Extensions are where the requirements hide.** "Payment declined",
   "GPS unavailable", "restaurant never responds" — the happy path is
   obvious; the extensions are the engineering. Markers read your
   extensions first (proj1a fast check: "Extensions non-trivial?").

Common failures, seen every year:

- Naming from the system's view ("Display status screen") instead of
  the actor's goal ("Track delivery").
- Steps that say *how* ("user clicks the blue button") instead of
  *what* ("customer confirms the order"). No widgets, no databases.
- Twenty variations of one use case ("login", "login with wrong
  password", "login with empty password"...). Those are extensions of
  ONE use case, not twenty use cases.
- Use cases for what the README promises, not what the code does. Your
  D2 covers the code. N1 said it: hidden features and dead code are
  findings.

### LLMs and use cases

Zero-shot ("write use cases for this app") produces mush: generic,
confident, wrong in quiet ways. Careful prompting — format first,
worked example, real evidence from the repo, checkable output — is
the difference proj1a asks you to measure. The
[proj1a prompts](../submit/1/proj1a.md) are the worked examples.

One tactic that works: make the LLM propose use cases, then YOU walk
the code to confirm each one. The LLM is the librarian (N1); you are
the judge. A use case you cannot trace to running code is a guess,
not a finding.

## 1. Testing essentials: checking what does happen (70 min)

> "Program testing can be used to show the presence of bugs, but
> never to show their absence." — Dijkstra

Why test? Because, overwhelmingly, code has bugs. Industry estimates
run 1–25 defects per thousand lines of delivered code; N1's evidence
table said generated code is fully correct barely a third of the
time. Bugs are not the exception you guard against; they are the
normal state of code you have not tested yet.

So Brooks (*Mythical Man Month*) budgeted 1/3 planning, 1/6 coding,
1/4 unit test, 1/4 system test — more testing than coding, fifty
years ago, and the ratio has not improved.

### Fault vs failure

- **Fault:** an incorrect step or definition sitting in the code.
- **Failure:** the moment something actually goes wrong at runtime.

They are not the same, and the gap matters. Discussion question: how
can a system with *few* pre-release faults have *many* post-release
failures?

Answer: nobody looked. An untested system reports few faults (none
found!) then fails heavily in production. A well-tested system exposes
many faults before release, so fewer failures after. Finding faults
is good news. Remember that when your proj1a tests start failing.

### The testing ladder

| Level | Checks | Example |
|---|---|---|
| Unit | One function, in isolation | `calculate_discount(price, pct)` returns the right number |
| Integration | Two parts, talking | Checkout service calls the payment gateway correctly |
| System | The whole flow, end to end | Cart → payment → confirmation email |
| Acceptance | The stakeholder's contract | Customer signs off that the system meets the requirement |

(Also in the wild: alpha and beta testing with real users, A/B tests
with statistics, and regression testing — re-run everything after
every change, which is why tests must be fast.)

Verification is climbing the ladder: "did we build the system right?"
Validation is the top rung: "did we build the right system?" Your use
cases (validation) tell your tests (verification) what to check.

### pytest, the essentials

One file, one function, one assert:

```python
# test_cart.py
def test_add_item_increases_total():
    cart = Cart()
    cart.add("apple", 2.50)
    assert cart.total() == 2.50
```

Run it:

```
pytest -v
```

That is 90% of what you need. The other 10%:

- **Test naming:** `test_<action>_<expected>`. The name is
  documentation — `test_declined_card_keeps_cart_unpaid` tells the
  reader what should happen without opening the code.
- **Arrange, act, assert:** set up the preconditions, fire the
  trigger, check the postconditions. Notice: that is the use case
  format, executed.

But note what pytest does NOT solve. Running tests is now trivial;
knowing WHAT to test is not. Every assert needs an expected value,
and something has to say what "expected" means. That something is an
**oracle**, and finding one is the persistent problem of testing —
the **oracle problem**. Your first oracle is your use case:
postconditions are oracles. If you cannot write the assert, your use
case was too vague; go fix it (that is the N1 loop, running). But
postconditions run out fast — what is the "expected value" of a
recommendation, a search ranking, a generated paragraph?

### The oracle problem: some ways out

**Solution 1: use an LLM as your oracle.** "Here is the input, here
is the output — is this right?" Cheap, fast, and it works, sometimes.
But now ask: who tests the test oracle? Another LLM? And who tests
that one? The recursion never grounds out, and N1's numbers apply at
every level (~52% of chatbot answers to programming questions contain
errors). Useful as a first filter; never as the final judge.

**Solution 2: mutation testing.** Flip the question. Instead of
asking "is the output right?", ask "would my tests notice if the code
were wrong?" Inject small deliberate bugs (mutants): swap a `<` for
`<=`, negate an if, drop a statement. Run your suite. Tests that kill
the mutants are doing work; mutants that survive mark code your suite
never truly checks. You still have no oracle for the program — but
you now have an oracle for your *tests*.

**Solution 3: properties and metamorphosis.** Sometimes you cannot
say what the right answer IS, but you can say how it must BEHAVE.
Property-based testing checks invariants over random inputs
(sorting output is always ordered; save-then-load returns what you
saved). Metamorphic testing checks relations between runs: searching
"cheap hotel" should return no FEWER results than "cheap hotel with
pool"; a route A→C should never beat A→B→C by violating the triangle
rule. No expected values anywhere — just relations that must hold.

**Solution N: use fewer tests (Menzies' research).** All the above
assume more checking is better. The counter-move: most tests tell
you almost nothing, so find the fewest, most informative tests and
run only those. Active-learning methods can often reach near-best
conclusions after labeling only a few dozen examples. When the
oracle is expensive — a human, a slow build, a paid API — economics
run the show: spend your scarce oracle calls where they buy the most
information. See [timm.fyi/ezr.html](https://timm.fyi/ezr.html).

### Edge cases

Bugs live at boundaries. For every input ask: empty? zero? negative?
huge? wrong type? duplicated? unicode? For every sequence ask: twice
in a row? out of order? interrupted halfway?

The happy path almost always works — that is why it is in the demo.
Edge cases are where your D3 failures (and marks) come from.

### The results table

D3 wants raw test output plus this table:

| Test | Why we tried it | Expected | What happened |
|---|---|---|---|
| `test_add_item_increases_total` | UC1 step 3 | total = 2.50 | pass |
| `test_declined_card_keeps_cart_unpaid` | UC1 extension 5a | order not created | **fail: order created anyway** |

Expected versus actual, side by side, in public. The second row is
the interesting one.

### Failures are findings

You are testing a year-old fork of someone else's code. Some tests
WILL fail — code rot, hidden assumptions, real bugs. Good. A failing
test plus a one-line explanation ("fails because the API this calls
sunset in March") is worth more marks than a suspiciously green
dashboard. The rubric says it directly: "Failures explained, or
hidden?" Hiding failures is the student version of slop (N1): your
green checkmark, the marker's review burden.

### Traceability

D4 is a table linking tests ↔ use cases, both directions:

- **Forward:** every use case has at least one test. Gaps explained.
- **Backward:** every test points at the use case it checks. A test
  that checks nothing anyone asked for is dead weight — or an
  undocumented requirement. Find out which.

Regulated industries live this way (avionics: every test traces to a
requirement). For you it is one table and it is the marker's fast
check: "does every use case have at least one test?"

Also in D4: judge the project's OWN tests against your use cases.
Where are they blind? That verdict — "their suite never touches
payment failures" — is exactly the kind of finding that fills a
report.

## 2. The demo video: showing your evidence (20 min)

Project 1a has no live demo. Instead: a 2–5 minute video of the
software actually running, linked in your report. **The video is 3 of
the 5 marks.** Budget effort accordingly.

What the marker wants to see, in order:

1. **The software runs.** Ten seconds of it doing its main thing.
2. **Your tests execute.** Real `pytest` output scrolling, not a
   screenshot of green.
3. **A pass AND a failure.** Show a failing test, then explain it in
   one sentence. A video with no failures reads as a video that is
   hiding something.
4. **One use case, end to end.** Pick your best one; walk it live.

Craft rules, learned the hard way:

- **Big fonts.** Bump the terminal to 18pt+ before recording. If the
  marker squints, you lose.
- **Script it first.** Write five bullet points, do one practice run.
  Unscripted videos run long and ramble.
- **2–5 minutes means 2–5 minutes.** Short and dense beats long and
  padded — same rule as the report.
- **Don't over-produce.** Screen capture plus your voice is plenty
  (QuickTime, OBS, or any screen recorder). No title cards, no music.
- **Narrate the failure.** The sentence "this test fails because the
  upstream API changed — that's code rot, documented in section 3" is
  the strongest fifteen seconds you can record.

Live demos start with Project 2. The video is practice for those:
same discipline, with an undo button.
