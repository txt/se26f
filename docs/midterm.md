# CSC510 Mid-term · Mon Oct 12 · 60 minutes · 24 marks
On the top right of EVERY page you hand in, write: your name, the last digits of your student ID, and "page M of N" (N = total pages you submit).
Eight questions; do ALL EIGHT (about 7 minutes each). Each question is worth 3 marks: (a) is short recall, 1 mark; (b) is a scenario containing exactly one mistake, 2 marks. No code is shown and none is asked for. Every question is a variant of the weekly review notes; if you did the weeklies, you have met every idea here.
1. **Prompting.** (a) Name the four parts of the standard prompt pattern. (b) A team debugs with this prompt: *"You are a test engineer reporting to our CTO. Below, pasted in full, are the bug report and the failing module. Reply as a table: file, line, cause, suggested fix. If you are not sure of a cause, give your best guess so the table is complete."* The scenario contains one mistake. Name it and say what happens if it persists — what the output contains, and what that does to work built on it (1 mark). Then, in English, say how to fix the prompt (1 mark).
2. **CI and badges.** (a) After a push, what is the only thing GitHub learns from your test run, and what do the green and red badges mean? (b) A team wrote its own test runner. It prints PASS or FAIL for every test and a final tally, then always finishes normally, signalling success to the operating system whatever the tally said. The CI workflow runs it on every push; the badge has been green for three weeks. Name the mistake and say what happens if it persists — what CI reports, and what that does to the team's work built on it (1 mark). Then, in English, say how to fix it (1 mark).
3. **Testable requirements.** (a) State the course rule for deciding whether a written requirement is testable. (b) The requirements document contains "R7: the app must be fast." The team marked R7 as *verified* after a hallway demo where the pages felt quick. Name the mistake and say what happens if it persists — what "verified" means at acceptance time, and what that does to the delivered product (1 mark). Then, in English, say how to fix R7 (1 mark).
4. **Layers.** (a) In the data / model / dialog stack, what does the dialog layer hold, and what does the model layer hold? (b) The rule "age runs 0 to 120" is coded only inside the web form. The model layer runs in the cloud, and two other writers also reach it: a mobile app and a nightly batch import. Name the mistake and say what happens if it persists — what enters the model, and what that does to everything computed from it (1 mark). Then, in English, say how to fix where the rule lives (1 mark).
5. **Coverage.** (a) What does line coverage measure, and what is the smoke-alarm rule for reading a coverage number? (b) A pull request declares the suite strong: "two tests give 100% line and 100% branch coverage, and both pass." The team agrees no further tests are needed and merges. Name the mistake and say what happens if it persists — what the suite actually checks, and what that does to code shipped behind it (1 mark). Then, in English, say how to fix the suite (1 mark).
6. **Deleting "unused" code.** (a) State the Microsoft ribbon finding: how much usage sat in how many of the sixty icons, and name two costs the unused icons were carrying. (b) A code sweep of a library that has been in the field for two years, and is used by thousands of developers, finds a module with no callers. To shrink the attack surface, a teammate deletes it that afternoon, bundled into the same commit as the week's feature work. Name the mistake and say what happens if it persists — what can break, and what recovering costs (1 mark). Then, in English, say how to do the deletion safely (1 mark).
7. **Undo.** (a) Define a closure and name its two parts. (b) A drawing app implements undo by saving a complete copy of the document after every edit. Demos go fine; users with big documents and long sessions report the app slowing down and then crashing. The team responds by capping undo at three levels. Name the mistake and say what happens if it persists — what the memory cost grows with, and what that does to users (1 mark). Then, in English, say how to fix the undo design (1 mark).
8. **Flaky tests.** (a) Name four common sources of test flakiness. (b) The team's norm for a red CI build is: "rerun it; if it goes green, merge." It usually goes green on the second or third try, so the norm now applies to every red build. Name the mistake and say what happens if it persists — what red comes to mean, and what that does to the suite as a safety signal (1 mark). Then, in English, say how to fix the team's policy (1 mark).

## Marker's key — cut before printing
Each (b): 1 mark = mistake named + consequence traced; 1 mark = fix in English. Concepts, not wording.
1. (a) A role; real evidence pasted in; a fixed output format; a ban on guessing (if unsure write UNKNOWN; cite file and line). (b) The last line inverts the fourth part: it *orders* the model to guess. Plausible invented causes and fixes fill the table, indistinguishable from real ones, and debugging time is spent chasing them. Fix: replace the last line with a ban on guessing — if unsure write UNKNOWN, and cite file and line for every claimed cause.
2. (a) One process exit code: 0 means green, anything else means red — that number is all CI knows. (b) The runner always signals success, so CI is blind: the badge stays green while tests fail, teammates pull broken code trusting it, and weeks of work get built on breakage. Fix: the runner must end by signalling failure to the operating system whenever any test fails (and the same tests should run locally before each push — the workflow only fires after the push).
3. (a) Testable = it has a number and an oracle; no oracle, no requirement. (b) R7 has neither, so "verified" is a mood, not a result: at acceptance, client and team can disagree forever, and performance can silently regress because nothing measures it. Fix: rewrite R7 with a metric, a threshold, and conditions — e.g. "95% of page loads under 2 seconds at 10,000 concurrent users" — and let verification mean that acceptance test passing.
4. (a) Dialog holds what *might* be true (a half-filled form is a fake); the model holds what *is* true. (b) The rule guards only one of three entrances: the mobile app and the batch import write ages like 130 straight into the model, the stored data goes bad, and everything computed from it (reports, analytics, decisions) inherits the corruption. Fix: give the rule one home that the model owns — the model validates every submit, and can publish the constraint for dialogs to check locally; the form keeps fast rejection without becoming the authority.
5. (a) Which lines some test visited. Low coverage is evidence the suite is weak; high coverage is not evidence the suite is strong. (b) Coverage is a disjunction: two tests can visit every line and both sides of every branch yet never test the branch *combinations*, and assertions may check nothing — so bugs ship behind a perfect dashboard and later regressions pass unnoticed. Fix: add tests for boundaries and branch combinations, and audit assertion strength with mutation testing.
6. (a) 90% of usage sat in 10 of 60 icons; costs (any two): visual clutter, user confusion, maintenance effort, reliability risk, attack surface. (b) "No callers" is a claim about your knowledge, not about the code (the coconut) — and two years in the field with thousands of users means the blast radius is other people's builds (left-pad): "no callers" only counts the callers you can see. Because the deletion is bundled with feature work, recovery means untangling a mixed commit instead of one revert. Fix: test the "unused" hypothesis first — search for references, instrument it in production for a release — then delete in its own dedicated commit so revert is one command.
7. (a) A function plus the variables captured from the scope where it was made — the body (code) and the captured environment (data). (b) Snapshot cost grows with document size times number of edits, so memory blows up on big documents; capping at three levels sacrifices the feature instead of fixing the design. Fix: record each edit's inverse operation instead — memory then grows with the size of the change, and a fixed-size circular buffer bounds the history at any depth you like.
8. (a) Timing, network behavior, test-order dependence, unseeded randomness. (b) Rerun-to-green teaches the team that red means noise: a genuine regression merges on a lucky rerun, and the suite stops being a decision signal — excellent tests, broken alarm. Fix: quarantine the flaky test the same day (a visible skip plus a ticket), then fix, replace, or delete it within the week; rerunning must never be the normal workflow.
