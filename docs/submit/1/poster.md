Each part of Project 1 hands in one poster (as a PDF, to Moodle):

- The [Project 1a](proj1a.md) poster sells the product **as it is** — its use
  cases, and your tests of it.
- The [Project 1b](proj1b.md) poster sells the **better product** you propose.

## Format

- Use one standard page (letter or A4).
- You can use small fonts (4 to 6 points).
- Submit one PDF file to Moodle.
- Do not leave large empty areas.
- Make it exciting. Keep it professional.

## Content

The poster must show:

- Your group number.
- The names of all group members.
- A mission statement paragraph. Give the **why** (the challenge you answer),
  the **what** (the thing you will build), and the **so what** (the benefits).
  Example: "Online content can be emotionally overwhelming. Our app helps make
  sense of it. Sentiment Analyzer Pro lets users analyze the emotional tone of
  text, images, news, speech, and YouTube comments. Whether you track brand
  sentiment, filter negativity, or just stay informed, the app makes emotional
  insight fast and accessible. With a Chrome extension and improved UI, it is
  now easier than ever to understand how content feels, not just what it says."
- The stakeholders (for example: admin, staff, customer — who else?). These can
  be part of the mission statement.
- QR codes, each with its URL printed underneath (so we can work from the QR
  code or from the URL), for:
  - Your repository.
  - Your discussion forum. The forum can be private, but CSC 510 tutors and
    lecturers must have access.
  - A video of a live demo (less than 5 minutes). How you host the video is
    your choice.
- Icons that show your proposed tech stack.
- Small screen snaps of the system. If your system is a CLI tool, show one call
  to the tool and its printed output.

## The demo

Projects 1a, 2, and 3 each include one live demo, worth 5 of that project's
marks. (Project 1b has no demo: its product is not built yet.) Be prepared to
demo the running system when asked. For that demo:

- Show up with the software already installed and running (on your laptop, or
  on the cloud). The demo must start straight away. No setup time.
- Provide one operator for the demo. The tutor watches the operator run the
  code.
- Demo scheduling rules (working hours, and optional after-hours slots):
  see the [policies](../lect/policies.md).

## Milestones

Show three groups of milestones. Each group has 3 to 5 milestones. Each
milestone must have a clear goal and a possible implementation plan.

- **Before:** the work that was done before (Project 1a).
- **Now:** the work you plan for this month (Project 2).
- **Future:** the work that is possible in the next month (Project 3).

Be ambitious. Dull milestones lose marks. But do not be too ambitious — you
must code this.

## Sell the software

- Show what is better now, because this code was written.
- Propose the better version (version i+1).
- Boast your test cases from Project 1a.

## Ways to lose points

- The poster or the demo does not have the features above.
- The poster does not sell the project:
  - After 15 seconds, a reader still does not know what the project is about.
  - The poster gives no good reason to care about the tech stack (for example:
    "Select this project to learn Kubernetes").
- You have too few test cases.
